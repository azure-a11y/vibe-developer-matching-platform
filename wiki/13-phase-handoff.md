# 13 — 이관 단계 CLAUDE.md

> "운영 이관 및 문서화"(`CLAUDE.md` "작업 단계별 원칙" 11단계) 작업을 시작하기 전에 이 문서를 먼저
> 엽니다. 프로젝트 완료는 코드 구현 종료가 아니라 이 단계까지 포함한다(`CLAUDE.md`).

## 언제 이 문서를 여는가

- 배포([12-phase-deployment.md](./12-phase-deployment.md)) 이후 운영자에게 인계하는 작업
- 운영 문서·계정·권한 정리

## 이관 체크리스트

`CLAUDE.md` "배포 및 이관" 절의 항목을 그대로 상속한다:

- [ ] Production build 확인
- [ ] 환경변수 목록 정리
- [ ] 배포 절차 정리
- [ ] 관리자 계정 및 권한 확인
- [ ] 데이터 구조 설명
- [ ] 운영자 콘텐츠 등록 방법
- [ ] 장애 발생 시 확인 항목
- [ ] 외부 서비스/API 목록
- [ ] 도메인 및 DNS 관련 정보
- [ ] 분석/SEO 도구 설정
- [ ] Git 저장소 및 브랜치 상태
- [ ] 알려진 이슈
- [ ] 유지보수 시 주의사항

## 이 프로젝트 고유 항목

### 관리자 계정·등급·권한 (FR-10)

운영자에게 다음을 설명한다:
- 등급 체계(최종 관리자/콘텐츠 관리자/검수 담당 — 예시값, PRD Q21에 따라 클라이언트 확인 후 확정된
  실제 등급명을 기재)
- 등급별 메뉴 접근 권한 매트릭스(대시보드/Builder/Work/Work Process/Insight/설정/계정·권한)
- 빌더 개별 권한 토글(Insight 작성/수정/삭제, 삭제는 기본 비활성)
- 빌더 업로드 콘텐츠는 항상 승인 대기로 등록되고 최종 관리자만 공개 전환 가능(FR-6 AC-6.4)

### 외부 서비스·API 계정 소유자 정리

PRD §8 "외부 의존"을 인계 문서로 그대로 활용한다:

| 서비스 | 확인할 것 |
| --- | --- |
| pluug | 폼 연동 방식(API/임베드/리다이렉트, Q7/Q20), 정식 계정 소유자 |
| Supabase | 정식(유료) 프로젝트 오너 권한 보유자 |
| GA4 | 클라이언트 계정 협업자 초대 상태 |
| 구글/네이버 서치콘솔 | 등록 계정, 소유권 확인 상태 |
| 도메인 | `builderschool.ai` 계승 여부 또는 신규 도메인(Q3), DNS 관리 주체 |

### 콘텐츠 등록 방법 (운영자가 재문의 없이 가능하도록)

- Insight 글 작성/수정: 관리자(`apps/admin`) 블로그 관리 화면(FR-5)
- 빌더 Work 업로드 → 승인: FR-6 플로우(빌더 업로드 → 승인 대기 → 최종 관리자 승인 → 공개)
- 프론트매터 필드를 새로 추가해야 하는 경우: `schema.ts` → admin 폼 → `audit.ts` 세 곳을 함께 수정해야
  한다는 점을 운영팀 개발 담당자에게 안내([01-architecture.md](./01-architecture.md) 확장 지점)

### 알려진 이슈는 새로 쓰지 않는다

[`docs/analysis/02-unfinished-features.md`](../docs/analysis/02-unfinished-features.md)를 그대로
인계 문서로 사용한다. 이관 시점에 이미 해결된 항목은 표시만 갱신하고, 문서를 새로 만들지 않는다.

## 이 단계에서 하면 안 되는 것

- 운영자가 코드를 몰라도 되는 작업(콘텐츠 등록, 승인)에 개발자 개입을 전제로 문서화하는 것
- 알려진 이슈를 숨기거나 축소해서 전달하는 것
- 계정 소유권 이관 없이 "완료"로 보고하는 것(예: Supabase 오너 권한이 팀장 개인 계정에 남아있는 상태)

## 다음 단계로 넘어가는 기준

- 이관 체크리스트 전 항목이 문서화됐고 운영자가 확인했다
- 계정 소유권이 실제로 클라이언트 측으로 이전됐다(팀 개인 계정에 남아있지 않다)
- 여기서 프로젝트 사이클이 종료된다. 이후 신규 요구사항은 다시
  [09-phase-design.md](./09-phase-design.md)부터 시작한다.
