# 09 — 디자인 단계 CLAUDE.md

> 이 문서는 `CLAUDE.md`(하드 룰)를 대체하지 않습니다. "디자인 방향 수립 / 와이어프레임·목업 / 디자인
> 확정"(CLAUDE.md "작업 단계별 원칙" 2~4단계) 작업을 시작하기 전에 이 문서를 먼저 엽니다.

## 언제 이 문서를 여는가

- Visual Direction(타이포·그리드·컬러 등)을 정하는 작업
- 와이어프레임·목업(HTML/Figma 등) 제작·수정
- 섹션 디자인 확정 논의
- 위 작업 중 "레퍼런스로 뭘 참고할지"를 판단해야 하는 순간

개발(코드 구현)만 하는 작업이면 [10-phase-development.md](./10-phase-development.md)를 대신 여세요.

## 먼저 참고할 문서 (중복 서술 없음 — 링크만)

- `CLAUDE.md` "UI/UX 디자인 품질 원칙" 절 — 목표 수준, 피해야 할 AI 디자인 패턴, 디자인 시작 전 10항목
- `CLAUDE.md` "기존 디자인 산출물 취급" 절 — 과거 시안을 자동 계승하지 않는다는 원칙의 원문
- `CLAUDE.md` "멀티에이전트 작업 원칙" 절 — 디자인은 병렬 위임 금지
- `wiki/memory/long-term/image-generation-policy.md` — 에셋(사진·일러스트)은 Codex `imagegen` 전용
- `docs/planning/AI빌더그룹_기획서.md` §8(디자인 퀄리티 기준), §6(소구점), §7(레퍼런스)
- `docs/planning/AI빌더그룹_PRD.md` FR-1(홈)·FR-2(Work)·FR-3(Insight)·FR-7(빌더 프로필)·FR-9(Eduinfo),
  NFR "디자인 신뢰도", 오픈이슈 Q11·Q18·Q19

## 목표 수준

전문 UI/UX 디자이너 또는 디지털 에이전시가 만든 B2B 브랜드 경험 수준을 목표로 한다. "AI가 빠르게 만든
랜딩페이지"처럼 보이는 결과를 허용하지 않는다(`CLAUDE.md` 원칙 그대로).

이 프로젝트에서는 이게 추상적 원칙이 아니라 **클라이언트가 명시한 핵심 성공 조건**이다.

> "가장 중요한 건 이 디자인 퀄리티가 절대 바이브 코딩으로 딸깍하고 만든 느낌이 나면 안 돼요."
> (기획서 §8.1 원문 인용)

핵심 판단 기준은 **섹션마다 인터랙션이 달라야 한다**는 것 — 전부 똑같은 fade-in만 반복하면 실패,
일부러 애니메이션을 넣지 않은 영역이 있어야 "사람이 만들었다"는 인상을 준다(기획서 §8.1).

## Visual Direction을 먼저 확정한다

구현부터 시작하지 않는다. 아래 10개 항목을 먼저 정의한다(`CLAUDE.md` 원칙, 이 프로젝트에 맞춰 재확인):

1. Visual Direction
2. Brand Mood
3. Typography
4. Grid / Layout
5. Spacing System
6. Color System
7. Image / Asset Direction
8. Interaction / Motion
9. Section Hierarchy
10. Responsive Strategy

이 10개가 정해지기 전에는 개별 섹션의 픽셀 단위 작업(색상 확정, 카드 레이아웃 확정 등)에 들어가지 않는다.

## 기존 산출물은 레퍼런스가 아니라 요구사항 확인 자료

`CLAUDE.md`가 지정한 대상(`docs/wireframes-3ans.html`, `docs/mockups-3ans.html`,
`docs/자료/2조/와이어프레임_프론트엔드/**`)에 더해, 이 프로젝트에서는 아래도 **같은 원칙**을 적용한다:

- `artifact/builder-group/**` — "Human Craft" 컨셉 라이브 목업(2026-08-12 2차 미팅에서 최종 후보 2안 중
  1안으로 선정됨)
- `artifact/admin/**` — 관리자 화면 시안(2026-08-13)
- `artifact/concepts/**` — 5개 컨셉 후보안 전체

이유: PRD v4 서문이 이들을 "아직 디자인 확정 이전 단계(작업 단계 3 — 와이어프레임/목업, 2개 시안 후보
상태)"라고 명시했다. 시안이 채택됐다는 사실이 "디자인 확정"을 의미하지 않는다 — 2차 미팅 피드백도
"상세 페이지 컴포넌트에 AI스러운 느낌이 남아있다"였다(기획서 §17.1, PRD FR-2 AC-2.6).

**적용 방식**: 이 자료들에서 확인하는 것은 요구사항(IA, 섹션 구성, 확정된 기능 정책)뿐이다. 색상·카드
구조·여백·타이포그래피·컴포넌트 스타일을 사용자가 명시적으로 "이 시안을 레퍼런스로 써라"라고 지정하지
않는 한 자동으로 계승하지 않는다.

**레퍼런스 분석 방식** (기획서 §8.2 원칙): 레퍼런스는 클라이언트가 주는 게 아니라 우리가 직접 픽하는
것이다. 그리고 참고하되 그대로 베끼지 않는다 — "이 UX가 정말 좋은가"를 스스로 검토한 뒤 반영한다
(예: 헤더가 넓어지는 인터랙션이 실제로 좋은 UX인지 판단, 기획서 §8.3).

## 하나의 디자인 시스템 — 섹션을 따로 취급하지 않는다

기획서·PRD의 실제 정보구조 기준으로, 아래 섹션은 서로 다른 디자인이 아니라 **하나의 디자인 시스템**으로
취급한다:

```
히어로 → 문제 제기 → 선택 기준 → 포트폴리오(Work) → 매거진형 카드(Insight)
→ 빌더(Builder) → 조직(About) → 일하는 방식(Work Process) → 인사이트 → FAQ → 문의
```

(참고: `artifact/builder-group` 목업의 실제 섹션 순서는 Hero → Work → Insight → Eduinfo → FAQ → About
→ Related Links → Footer. 위 목록은 PRD 요구사항 관점의 논리적 섹션이며, 실제 화면 순서·명칭은 디자인
확정 단계에서 조정될 수 있다.)

**섹션별 독립 병렬 디자인 금지** — 하나의 책임 주체가 전체 Visual Direction을 먼저 결정한 뒤에만
컴포넌트 구현을 병렬화한다(`CLAUDE.md` "멀티에이전트 작업 원칙"). 여러 에이전트에게 "Hero는 A가,
Work는 B가" 식으로 동시에 디자인을 맡기지 않는다.

## 체크리스트

| 항목 | 확인할 것 |
| --- | --- |
| Typography | 위계(제목/본문/캡션)가 명확한가. 브랜드 고유성이 있는가(범용 SaaS 폰트 조합 지양) |
| Grid | 섹션마다 동일한 그리드 폭을 기계적으로 반복하지 않는가 |
| Spacing | 충분한 여백과 밀도 조절이 있는가 (모든 섹션이 비슷한 높이로 나열되지 않는가) |
| Color | 브랜드 컬러 시스템이 정의됐는가. 의미 없는 그라데이션·glow·glassmorphism 남용 여부 |
| Asset Direction | 사진/일러스트는 Codex `imagegen` 산출물 또는 실제 제공 에셋인가 → [image-generation-policy.md](./memory/long-term/image-generation-policy.md) |
| Motion | 섹션마다 인터랙션이 다른가. 전부 같은 "아래→위" fade-in 반복이 아닌가(기획서 §8.1 반례: Ten AI) |
| AI스러운 카드 반복 방지 | 모든 콘텐츠를 둥근 카드에 넣거나, 같은 형태의 3열 카드를 반복하지 않는가(`CLAUDE.md` "피해야 할 전형적인 AI 디자인" 목록) |
| Hero 품질 기준 | 3사(똑똑한 개발자·이솝·크몽) 소개 없이 "바이브 코딩 외주"임이 즉시 전달되는가(PRD FR-1 AC-1.1). 장식이 실제 콘텐츠보다 강하지 않은가 |
| Work 레이아웃 | 포트폴리오 개수·화려함이 아니라 "일하는 방식 + 맞춤 매칭"이 소구되는가(PRD D5, 기획서 §6) |
| 실제 포트폴리오 이미지 활용 원칙 | 목업 단계의 샘플/플레이스홀더 데이터를 실제 프로젝트로 교체할 지점이 명확히 표시돼 있는가(PRD FR-2 AC-2.1·AC-2.5 — 목업/가상 사례 금지) |
| 모바일 반응형 | 반응형 전략이 Visual Direction 단계에서부터 설계됐는가(사후 대응이 아닌가) |
| 레퍼런스 분석 방식 | 레퍼런스를 직접 픽했는가, 그대로 베끼지 않고 UX를 검토했는가(기획서 §8.2·§8.3) |

## 이 단계에서 하면 안 되는 것

- 사용자가 지정하지 않은 과거 목업·시안의 색상/컴포넌트/카드 구조를 자동으로 계승하는 것
- "저렴함"을 소구하는 카피·디자인 톤(기획서 §2.5 — 반반외주 실패 사례 반면교사)
- 3사(똑똑한 개발자·이솝·크몽) 소개 섹션 신설(PRD D1, Out of Scope)
- 섹션별로 서로 다른 에이전트에게 독립 병렬 디자인 위임
- 디자인 확정 전에 구현 편의를 이유로 Visual Direction을 단순화

## 다음 단계로 넘어가는 기준

- 10개 Visual Direction 항목이 문서화됐다
- 11개 섹션이 하나의 시스템으로 일관되게 스타일 정의됐다(개별 섹션 디자인이 아니라 시스템 검토 완료)
- 팀장 2인 검토를 통과했다(투표 금지, 기획서 §10.2 의사결정 원칙)
- 여기까지 통과하면 [10-phase-development.md](./10-phase-development.md)로 넘어간다 — 승인된 디자인을
  개발 편의로 임의 단순화하지 않는다.
