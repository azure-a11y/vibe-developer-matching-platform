## 1. 카피 정책

### 1.1 "저렴함" 소구 금지

**규칙**: 랜딩 카피에서 "저렴함"을 절대 소구하지 않는다. 대신 "체계성과 검증된 실력"을 소구한다.

**근거**: 반값 외주("반반외주", 스파르타코딩클럽 실패 사례) → "싼 게 비지떡" 인식 → 실패. 고객 심리는
"500만 원으로 이상한 거 만들 바에 1,000만 원 주고 제대로 된 걸 만들겠다"(가격 역설). 우리 교육생은
똑빌더 등 시스템으로 체계적으로 보완되므로 동일한 실력이라는 논리로 소구한다. (기획서 §2.5)

### 1.2 1기 운영 방식과 사이트 문구의 의도적 불일치

**규칙**: 실제로는 1기가 전원 진행이지만, 사이트에는 "우리가 선별한 잘하는 분들 위주로만 진행한다"고
표기한다.

**근거**: 거짓말이 아니다 — 2기부터는 실제로 선별 배정 + 미달자 전액 환불로 운영된다. 1기는 이미
전원 진행을 약속했기 때문에 실제 운영과 문구가 다를 뿐이다. (기획서 §2.4)

**적용 시 주의**: 카피 작성자는 이 표를 반드시 참고한다.

| | 실제 운영 | 사이트에 쓸 문구 |
| --- | --- | --- |
| 1기 | 전원 동일하게 진행 | "우리가 선별한 잘하는 분들 위주로만 진행한다" |
| 2기부터 | 잘하는 사람만 선별 배정, 부적합자는 전액 환불 | 동일 |

### 1.3 딸깍 방지 — 인터랙션 다양성

**규칙**: 섹션마다 인터랙션이 달라야 한다. 일부 섹션은 의도적으로 애니메이션을 넣지 않는다(강약
조절 자체가 판단 기준). 모든 섹션·텍스트·컴포넌트가 동일한 애니메이션을 반복하면 탈락.

**근거**: "가장 중요한 건 이 디자인 퀄리티가 절대 바이브 코딩으로 딸깍하고 만든 느낌이 나면 안 돼요."
사람이 만들었다는 인상은 강약 조절(안 움직이는 영역의 존재)에서 나온다. (기획서 §8.1)

### 1.4 레퍼런스 선정 주체

**규칙**: 디자인 레퍼런스는 클라이언트가 주는 게 아니라 우리 팀이 직접 픽한다. 클라이언트 요구는
"이런 느낌으로" 정도이며, 되물어서 우리가 구체화해 제안한다.

**근거**: 레퍼런스를 스스로 골라 제안하는 것 자체가 실력의 증거. (기획서 §8.2)

## 2. 콘텐츠 진실성 정책

### 2.1 Work는 실제 수행 프로젝트만

**규칙**: Work(포트폴리오)에는 실제로 수행한 프로젝트만 게시한다. 목업/가상 사례는 절대 포함하지
않는다.

**근거(반면교사)**: 포트폴리오 수백 개를 전부 목업으로 채워 신뢰를 잃은 업체 사례. (기획서 §7.2,
PRD AC-2.1)

**현재 상태**: 목업의 프로젝트 카드·빌더 정보는 전부 샘플/플레이스홀더 — 실제 배포 전 반드시
실데이터로 교체 필요(PRD AC-2.5).

### 2.2 SEO 범위는 테크니컬 세팅까지

**규칙**: SEO는 구글·네이버 기본 테크니컬 세팅까지만 한다. GEO/AEO는 별도 대응하지 않는다("따라
온다"는 판단). 3주 일정에서 스스로 범위를 늘리지 않는다.

**근거**: "기본적으로 SEO만 잘 되면 된다. GEO는 따라온다." 단, 테크니컬 세팅이 완벽해도 콘텐츠를
AI로 대충 찍어내면 저품질로 떨어진다 — 콘텐츠 품질은 작성자 역량 문제이며 이번 구축 범위는 아니다.
(기획서 §9.3)

### 2.3 트래킹 목적의 URL 분기

**규칙**: 옵션에 따라 화면이 바뀌는 UI(예: FAQ)는 단순 화면 전환이 아니라 URL 슬러그를 바꾼다.

**근거**: 목적은 SEO가 아니라 GA 트래킹 — 사용자가 어느 옵션을 더 많이 클릭하는지 데이터로 확인해
메뉴 순서 등 의사결정 근거로 쓴다. (기획서 §9.1)

### 2.4 요소 단위 전환 추적과 실측 리스크

**규칙**: 신규 UI 요소(특히 CTA 성격의 버튼)를 추가할 때는 배포 전후 GA 전환 추이를 반드시 비교
검증한다.

**근거(실측 사례)**: FAQ 옆에 "소개서 다운받기" 버튼을 추가했더니 주간 문의가 10~20건 → 0건으로
떨어졌다. 버튼 제거 후 원복. 버튼 하나가 전환을 크게 떨어뜨릴 수 있다는 것이 이 프로젝트 전체가
트래킹을 필수로 요구하는 근거다. (기획서 §9.2)

## 3. 발행 게이트 정책

> Insight(구 Blog)뿐 아니라 Work·Builder 콘텐츠 전반에 동일 원칙이 적용된다. `CLAUDE.md` 하드 룰
> 2·4의 프로젝트 확장판이다.

### 3.1 발행은 사람만

**규칙**: 에이전트/Claude는 콘텐츠를 `in_review`(Insight) 또는 `승인 대기`(Work) 상태까지만 올린다.
`published`/`공개` 전환은 사람(최종 관리자)만 수행한다.

**근거**: `CLAUDE.md` 하드 룰 2. 모델이 자기 결과물을 평가하면 통과 쪽으로 기운다.

### 3.2 검수 게이트는 결정적으로

**규칙**: `packages/content/src/audit.ts`(발행 게이트)에 LLM 호출을 넣지 않는다. 사람과 에이전트가
항상 같은 규칙, 같은 결과를 봐야 한다.

**근거**: `CLAUDE.md` 하드 룰 4.

### 3.3 빌더 업로드는 등급·권한과 무관하게 항상 승인 대기

**규칙**: 빌더가 업로드한 Work·Insight는 해당 빌더에게 어떤 권한이 부여돼 있든(예: Insight
작성/수정 권한이 있어도) 항상 승인/검수 대기 상태로 등록된다. 공개(발행) 전환은 최종 관리자
권한이 있어야만 가능하다.

**근거**: 기획서 §5.1 — "하드 룰 2와 동일한 원칙 적용"이라고 명시. PRD FR-6 AC-6.4, FR-10 AC-10.3.

## 4. 권한 정책 (관리자 · 빌더)

> 상세 매트릭스 값(등급 이름·범위)은 클라이언트 확인 전이라 예시 수준이다(Q21, 아래 §4.4). 구조
> 원칙만 이 문서에서 확정한다.

### 4.1 관리자 등급 · 메뉴 권한

**규칙**: 관리자 계정은 등급(예: 최종 관리자 / 콘텐츠 관리자 / 검수 담당)을 가지며, 등급별로
대시보드·Builder·Work·Work Process·Insight·설정·계정·권한 7개 메뉴 각각에 대해 **전체 / 편집·승인
/ 조회 / 접근불가** 수준을 개별 설정할 수 있다.

**근거**: PRD FR-10 AC-10.1, AC-10.2.

### 4.2 빌더 개별 권한

**규칙**: 빌더 로그인 후 사용 가능한 메뉴는 관리자가 빌더별로 개별 토글한다. 기본값은 "본인 Work
업로드"만 허용. Insight 작성/수정/삭제 권한은 관리자가 개별로 켜고 끌 수 있으며, **삭제 권한의
기본값은 비활성**이다.

**근거**: 기획서 §5.1, PRD FR-6 AC-6.4, FR-10 AC-10.3.

### 4.3 인증 · 계정 표시 · 비밀번호

**규칙**:
- 로그인이 필요한 관리자·빌더 화면은 전용 로그인(이메일·비밀번호)을 통과해야 한다.
- 로그인 후에는 사이드바 등 상시 노출 영역에 현재 로그인한 계정의 이름과 등급을 항상 표시한다.
- 로그인한 계정은 본인 비밀번호를 변경할 수 있다. 관리자 등급은 추가로 다른 계정의 비밀번호를
  강제 초기화할 수 있다.
- 미인증 사용자는 어떤 등급의 화면에도 접근할 수 없다.

**근거**: PRD FR-10 AC-10.4~AC-10.6.

### 4.4 현재 구현 상태와의 격차 (선행조건)

**현재 상태**: `apps/admin`(:3001)은 실제 인증이 구현되지 않은 무인증 로컬 데모 상태다
(`docs/analysis/05-work-orders.md` WO-3).

**규칙**: 위 §4.1~4.3의 FR-10 권한 정책은 **실제 인증 구현이 선행돼야 실효성이 생긴다**. WO-3(Basic
Auth)는 FR-10이 요구하는 등급별 세분 권한에 비해 너무 얕으므로, WO-3는 그대로 구현하지 않고 이
정책(계정 테이블 + 등급 + 메뉴 권한 매트릭스) 구현에 흡수한다.

**근거**: `docs/planning/AI빌더그룹_프로젝트전환계획.md` §3.3.

### 4.5 확인 필요 (Q21)

등급 이름·개수(최종 관리자/콘텐츠 관리자/검수 담당)와 메뉴별 세부 권한 범위는 `artifact/admin` 시안
수준이며 클라이언트 확인 전이다. 코드에서는 등급을 하드코딩하지 말고 데이터로 관리해, 이름이
바뀌어도 구조 변경 없이 대응 가능하게 한다.
