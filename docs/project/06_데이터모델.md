# 06. 데이터모델 — 초안

> 작성일 2026-08-14 · 상태: 초안(v1) — 설계 방향, 필드명/타입 확정 아님
> 소스: `docs/planning/AI빌더그룹_프로젝트전환계획.md` §5, `03_기능명세.md`, 기존 `packages/content/src/schema.ts`
> 스키마는 디자인 확정(Q18)과 독립적으로 지금 착수 가능하다(전환계획 §4). 실제 zod 스키마 구현 시
> `packages/content/src/schema.ts`의 기존 패턴(`ImageSchema`, `SeoSchema`, `prefault()` 사용법 등)을
> 그대로 따른다 — 새 규칙을 만들지 않는다.

---

## 1. 원칙

1. 하드 룰 3(`getRepository()` 경유)을 그대로 유지한다 — 도메인이 늘어나도 앱 코드는 저장소 구현
   (file/Supabase)을 직접 알지 못한다.
2. 기존 `Post`는 삭제하지 않고 **`Insight`로 개명 + 재사용**한다 — SEO/GEO/Review 구조가 이미 FR-3
   요구사항과 대부분 일치한다.
3. 신규 도메인마다 `schema.ts`에 zod 스키마 → `repo/types.ts`에 인터페이스 → `repo/file.ts` /
   `repo/supabase.ts`에 드라이버 순으로 기존 패턴을 반복한다.
4. 브랜드명·pluug URL 등 확정되지 않았거나 바뀔 수 있는 값은 코드에 하드코딩하지 않고 `SiteSettings`
   로 뺀다(`04_정책정의.md` §4.5와 동일한 이유).

---

## 2. ERD (개념 수준)

```
Builder ──1:N──> Work (builderIds[] 로 N:M — 다수 빌더가 한 프로젝트에 참여 가능)
Builder ──1:N──> Insight (authorBuilderId, optional)

Work ──N:M── Builder (참여 빌더)

AdminAccount ──정의── (등급별 메뉴 권한 매트릭스: dashboard/builder/work/workProcess/insight/settings/accountPermission)
AdminAccount ──개별 토글── Builder (Insight 작성/수정/삭제 권한)

WorkProcess, Eduinfo, SiteSettings — 다른 도메인과 참조 관계 없는 독립 콘텐츠/설정
```

Work·Builder는 N:M — Work 쪽에 `builderIds: string[]`, Builder 쪽은 역참조(쿼리 시 계산, 별도 필드
저장 안 함 — 기존 file 드라이버 패턴상 조회 시 필터링이 더 간단).

---

## 3. 도메인별 스키마 초안

> 필드는 방향성이며 확정 아님. `?`는 optional, `[]`는 배열. 실제 구현 시 `ImageSchema`/`SeoSchema`
> 등 기존 재사용 가능한 서브스키마는 그대로 가져다 쓴다.

### 3.1 Insight (기존 `Post` 개명, 변경 최소화)

`PostFrontmatterSchema`를 그대로 유지하고 아래만 추가/재정의한다.

```
author: string                          → authorBuilderId?: string  (신규, optional 추가 — 기존 author 필드는 유지, 마이그레이션 없이 추가)
category: string                        → 값 집합만 재정의: "일하는 방식" | "AI 활용 공유회" | "빌더가 쓴 글" (코드 강제 아님, 문서화만)
```

나머지 필드(`title`, `slug`, `status`, `seo`, `geo`, `review`, `cover` 등)는 변경 없음.

### 3.2 Builder

```
Builder
  id: string
  displayName: string
  slug: string                          (SLUG_PATTERN 재사용)
  avatar?: Image                        (ImageSchema 재사용)
  bio: string
  specialties: string[]
  education: string[]
  communityActivity: string[]
  verifications: string[]
  status: 'pending' | 'active' | 'inactive'
  permissions: {
    canWriteInsight: boolean            (기본 false)
    canEditInsight: boolean             (기본 false)
    canDeleteInsight: boolean           (기본 false — `04_정책정의.md` §4.2)
  }
  createdAt / updatedAt: string
```

- `Work.builderIds[]`, `Insight.authorBuilderId`가 이 엔티티를 참조한다(역참조는 조회 시 계산).
- FR-7(빌더 프로필)의 IA 필드는 기획서 §3.5 기준 — 참여 프로젝트/작성 콘텐츠는 저장하지 않고 Work·
  Insight 조회로 파생한다.

### 3.3 Work (프로젝트)

```
Work
  id: string
  title: string
  slug: string
  summary: string
  scope: string                         (수행 범위)
  builderRole: string                   (빌더 역할)
  period: string                        (작업 기간)
  techStack: string[]
  problem: string
  solution: string
  result: string
  assets: Image[]
  builderIds: string[]                  (참여 빌더, N:M)
  status: 'pending_review' | 'published' | 'archived'
  createdAt / updatedAt: string
```

- `status`는 Insight의 `PostStatus`와 이름을 다르게 뒀다 — Work는 "예약 발행" 개념이 없고 승인
  게이트만 있으므로 상태 종류가 다르다(`04_정책정의.md` §3.3 참조).
- 0건이어도 배포 가능해야 한다(PRD AC-2.3) — 스키마 자체에는 제약 없음, 화면(web) 쪽에서 빈 상태
  처리.

### 3.4 WorkProcess

```
WorkProcess
  id: string
  title: string
  body: string
  order: number
```

- 기획서·PRD 모두 이 도메인은 얕게만 언급됨(§3.2 표에서 "Open"으로 표기) — 03_기능명세.md에 별도
  FR 없음. 관리자 메뉴는 존재하나(기획서 §5.1) 공개 페이지 요구사항은 `04_정책정의.md`·기획서 어디도
  상세 정의 안 함. **확인 필요**: WorkProcess가 공개 웹에 별도 페이지로 노출되는지, 관리자 전용
  콘텐츠인지.

### 3.5 Eduinfo (강의)

```
Eduinfo
  id: string
  title: string
  youtubeUrl: string
  pdfUrl?: string                       (Q13 미확정 — 현재 placeholder)
  order: number
  description: string
```

### 3.6 AdminAccount

```
AdminAccount
  id: string
  email: string
  name: string
  grade: string                         (예: '최종관리자' | '콘텐츠관리자' | '검수담당' — Q21 미확정, 하드코딩 금지 → grade는 자유 문자열 + 별도 GradeDefinition 테이블/설정으로 관리 권장)
  passwordHash: string
  menuPermissions: {
    dashboard: PermissionLevel
    builder: PermissionLevel
    work: PermissionLevel
    workProcess: PermissionLevel
    insight: PermissionLevel
    settings: PermissionLevel
    accountPermission: PermissionLevel
  }
  createdAt / updatedAt: string

PermissionLevel = 'full' | 'edit_approve' | 'view' | 'none'
```

- Q21(등급 이름·범위 미확정) 때문에 `grade`를 enum으로 고정하지 않는 것을 권장 — 클라이언트 확인
  후 좁혀도 마이그레이션 비용이 적다.

### 3.7 SiteSettings

```
SiteSettings (key-value)
  pluugFormUrl: string
  brandName: string                     (Q1 미확정 — 하드코딩 금지 강제 장치)
  domain?: string                       (Q3 미확정)
```

- `04_정책정의.md` §4.5, 전환계획 §3.4와 동일한 이유 — 미확정 값을 코드에 박지 않기 위한 설정
  저장소.

## 4. 저장소 레이어 확장 방향

기존 `packages/content/src/repo/`는 `Post` 전용이다. 신규 도메인마다 동일 패턴 반복:

```
repo/types.ts    — 도메인별 Repository 인터페이스 추가 (getAll/getBySlug/save/remove 등 기존 시그니처 재사용)
repo/file.ts     — file 드라이버 먼저 구현 (Phase 2 Exit 기준: file 드라이버 CRUD가 admin 없이 스크립트로 검증됨)
repo/supabase.ts — Supabase는 Phase 3에서, 마이그레이션은 packages/supabase/migrations에 신규 테이블 추가
```

`getRepository()` 진입점 패턴은 그대로 유지 — 앱 코드는 도메인이 늘어도 드라이버를 직접 모른다.
