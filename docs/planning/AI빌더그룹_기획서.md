## 1. 한 줄로 정리하면

**"바이브 코딩으로 외주 개발을 받아주는 회사"의 영업용 웹사이트(랜딩 페이지 + 관리자 페이지)를 만드는 프로젝트입니다.**

- 교육 사업(AI 빌더 스쿨)을 홍보하는 사이트가 **아닙니다.**
- 고객이 들어와서 **"우리 프로젝트 좀 개발해주세요"라고 의뢰를 넣는 사이트**입니다.
- 이번 건은 연습이 아니라 **진짜 외주**입니다. 기획·디자인·개발·검수 전부 실무 수준으로 관리됩니다.
- **핵심 성공 조건은 딱 두 가지**입니다. ① 딸깍(AI로 대충 찍어낸) 느낌이 나지 않는 디자인 ② 전환을 추적할 수 있는 트래킹 구조.

| 항목 | 내용 |
| --- | --- |
| 일시 | 2026-08-05(수) 14:06~14:44 (37분 55초) |
| 클라이언트 | 발주 담당자(똑똑한 개발자 소속, 주 발화자) 외 1인 |
| 수행팀 | 조유리, 한도균 |
| 공유 자료 | IR 자료(화면 공유), 디자인 레퍼런스(추후 별도 전달) |
| 다음 미팅 | 주간 정기 미팅(매주) — 목업 리뷰 |
| 프로젝트 기간 | 총 3주 (제작 2주 + 환경세팅·이관 1주) |

## 2. 왜 이 프로젝트를 하는가 (사업 배경)

이 부분을 모르면 디자인·카피 방향을 잘못 잡기 쉽습니다. 반드시 읽어야 하는 배경입니다.

### 2.1 기존 교육 플랫폼(패스트캠퍼스, 클래스101류)의 문제

- 마케팅비가 매출의 40% 이상을 먹습니다. 1,000만 원 벌면 300~400만 원이 광고비로 나감. 구조적으로 "자극적인 광고 + 낮은 콘텐츠 퀄리티"가 반복됨.
- 강사가 실제로 밑짐: 촬영 100시간 들여서 편집본 10시간을 만드는데, 제작 기간은 한 달도 안 줌. 유일한 유인이던 "브랜드 인지도"조차 약해지는 중.
- 이런 플랫폼은 애초에 100억~200억 매출이 목표라서 개별 강의 퀄리티가 구조적으로 낮을 수밖에 없음. 간혹 나오는 잘하는 사람들 덕분에 유지되는 구조.

**→ 그래서 이 팀은 "퀄리티 중심", "성과 중심"으로 방향을 잡았습니다.**

근거가 된 실험: 같은 웨비나를 두 번 진행했더니—

| | A(이솝 님 진행) | B(발주 담당자 진행) |
| --- | --- | --- |
| 참석자 | 약 200명 | 약 600명 |
| 결제 | 발생 | 0건 |

사람이 더 많이 왔던 B가 오히려 매출 0건. 이솝 님은 한 달간 직접 외주를 수행한 경험을 교육에 녹였고 본인이 참여해 피드백하며 고도화했지만, 600명 세션은 준비가 부실했음. 차이는 **"준비를 얼마나 진심으로 했는가"**였습니다. 그래서 앞으로는 "제대로 된 가치를 전달하는 것"이 장기적으로 사업을 지속시킨다는 결론을 내렸습니다.

### 2.2 4단계 사업 구조 (지금 우리가 만드는 건 이 중 어디쯤인가)

```
[1차] 유료 커뮤니티 → [2차] 교육(3트랙) → [3차] 일감 매칭·자생 → [4] 인재 내재화
```

| 단계 | 무엇을 하는가 | 비고 |
| --- | --- | --- |
| ① 유료 커뮤니티 | AI 네이티브로 100% 운영, 운영진 1~2명. 벤치마크는 "메모어"(3개월 기수제, 기수당 약 1,000명, 1인 약 20만 원, 환급제) | 목표: 올해~내년 유료회원 500명 (발주 담당자 본인 표현으로 "낮은 목표치") |
| ② 교육 3트랙 | 바이브 코딩 / AX 컨설턴트 양성 / AI 네이티브 창업 | 이번 사이트에서 AX 컨설팅은 **제외** |
| ③ 일감 매칭·자생 | 크몽 영업 조직을 활용해 리드를 수주 → 수료생에게 매칭 | **이번 프로젝트가 여기 해당** |
| ④ 인재 내재화 | 실제 외주 경험을 쌓은 수료생을 똑똑한 개발자가 채용 | 형태 미확정(기본급+성과급 / 정규직 / 파트너십 프리랜서) |

**커뮤니티가 왜 1차 목표인가**: IT/AI는 신규 툴이 계속 쏟아져서 교육만으로는 커버가 안 됩니다. 예를 들어 최근 도입한 개발 툴 "Orca"는 첫 교육 시점에는 존재 자체를 몰랐고, 발주 담당자 본인도 이제 막 사용 1주차라고 언급함. 그래서 스터디·정보 공유가 가능한 유료 커뮤니티가 필요함.

**핵심: 우리가 만드는 사이트는 ③단계, 즉 "일감을 실제로 수주하기 위한 영업 사이트"입니다.**

③이 중요한 이유(=4단계 목표): 잘하는 수료생이 **월 400만 원 이상** 벌어가는 사례를 만들어야 함. 그래야 ④단계에서 "이 사람 진짜 실력 있다"는 확신을 갖고 채용할 수 있기 때문(현재 AI 빌더 채용을 시도했지만 전부 실패 — 지원자들이 포트폴리오는 여러 개 들고 오지만 실전 외주 경험이 없어 면접에서 확신이 생기지 않았음).

투트랙 운영(일감 매칭 단계): 소규모 프로젝트는 AI 빌더에게 매칭, 큰 프로젝트는 개발 베이스가 깊은 개발자 다수를 투입. 예: 200만 원짜리 프로토타입 건이 들어오면 기능을 축소하거나 500만 원 규모로 재수주해서 매칭.

### 2.3 3개 회사가 얽혀 있는 구조

```
        똑똑한 개발자 ── 이솝 님의 교육 회사 ── 크몽
                          │
        ┌─────────────────┴──────────────────┐
        │   AI 빌더 그룹 (가제, 상위 브랜드)      │  ← 이번 프로젝트 대상
        │     · 바이브 코딩 외주 수주            │
        │     · (향후) AX 컨설팅                │
        └─────────────────┬──────────────────┘
                          │
                 AI 빌더 스쿨 (교육 사업, 기존)
```

- 3사 협업: 똑똑한 개발자 / 이솝 님(교육) / 크몽(영업 리드)
- 브랜드명 후보: AI 빌더 그룹 / 크루 / 팀 (미확정, "AI 빌더"는 고정)
- 도메인: 기존 `builderschool.ai` 계승 가능, 또는 `buildergroup.ai` 같은 신규 도메인 구매도 가능. 세팅은 발주 담당자가 이솝 님과 협의해 처리.
- 기존 `builderschool.ai`의 로고·컬러는 이솝 님이 만들어둔 자산으로 **참고는 가능**하지만, "그냥 대충 만든 것"이라 그대로 계승할 필요는 없음.

### 2.4 1기·2기 운영 방식 — 실제 운영과 사이트 문구가 다르니 주의

| | 실제 운영 | 사이트에 쓸 문구 |
| --- | --- | --- |
| 1기 | 전원 동일하게 진행(이미 약속했으므로) | "우리가 선별한 잘하는 분들 위주로만 진행한다" |
| 2기부터 | 잘하는 사람만 선별 배정, 부적합자는 전액 환불 | 동일 |

**카피라이터 주의사항**: 실제로는 1기가 전원 진행이지만, 사이트에는 "엄선된 인력"이라고 써야 합니다. 거짓말이 아니라 2기부터는 실제로 그렇게 운영되기 때문. 원문: *"1기분들은 저희가 다 약속을 했잖아요. 그렇기 때문에 모두 다 동일하게 저희가 진행할 건데, 우리가 선별한 잘하는 분들 위주로만 진행할 거다라고 이제 사이트에 들어가야 될 것 같아요."*

### 2.5 반드시 피해야 할 실패 사례: "반반외주"(스파르타코딩클럽)

- 교육생이 직접 수행 → 반값에 제공 → "싼 게 비지떡"이라는 인식 → 실패
- 고객 심리: "500만 원으로 이상한 거 만들 바에 1,000만 원 주고 제대로 된 걸 만들겠다" (가격 역설)
- **→ 그래서 랜딩 카피에서 "저렴함"을 절대 소구하면 안 됩니다.** 대신 "체계성과 검증된 실력"을 말해야 합니다. 우리 교육생은 똑빌더 등 시스템으로 체계적으로 보완되므로 동일한 실력이라는 논리.

## 3. 사이트 구조 (정보 구조 / IA)

```
AI 빌더 그룹 홈
├─ Work          → 포트폴리오 (참여 빌더 표시 → 빌더 프로필로 연결)
├─ Insight       → 콘텐츠/블로그 (카테고리를 우리 색깔에 맞게 재구성)
├─ (콘텐츠/유튜브) → 이솝 님 유튜브 (Insight 하위 or 별도 상위 탭, 검토 필요)
├─ 문의하기       → pluug 폼 연동 (영업 CRM으로 리드 전달)
└─ 관리자 페이지  → 블로그 관리 + 유저(빌더) 관리
```

### 3.1 첫 페이지가 전달해야 할 메시지

> "결국에는 우리가 제공하는 서비스가 **바이브 코딩으로 외주를 해드립니다**가 첫 번째."

첫 진입 시 "여기는 이런 곳이구나"가 즉시 전달돼야 함. 3사 소개 섹션은 불필요. AX 컨설팅은 이번 범위 제외(아직 서비스 자체가 없음, 다음 릴리즈에서 고도화).

### 3.2 Work (포트폴리오)

- 실제로 수행한 프로젝트만 올림 (반면교사: 어떤 업체는 포트폴리오 수백 개를 전부 목업으로 채워서 신뢰를 잃음)
- 프로젝트마다 **참여한 빌더**를 표시 → 클릭하면 빌더 프로필로 연결
- ⚠️ 오픈 시점 콘텐츠는 아직 미정 (신규 브랜드라 포트폴리오가 부족한 게 리스크). 다만 회의 중 "워크가 있으면 지금 저희는 똑똑한 개발자에서 한 거니까 이거 자체가 저희 일"이라는 발언이 있어, **똑똑한 개발자의 기존 실적을 초기 콘텐츠로 전용할 가능성**이 시사됨(3사 협업 관계상 가능 여부·표기 방식은 확인 필요 — §12 Q4).

### 3.3 Insight (콘텐츠/블로그)

카테고리 방향(발주 담당자 아이디어):
- 일하는 방식(업무 프로세스) — 소구점과 직결
- AI 활용 공유회 — 내부에서 AI를 어떻게 쓰는지 공유
- 빌더가 직접 쓴 글 → 그 빌더의 프로필로 연결

마케팅팀이 지속 발행할 콘텐츠 예시:
- "바이브 코딩을 잘하고 못하는 기준은 무엇인가"
- "요즘 바이브 코딩으로 외주하는 업체가 많은데 조심해야 합니다"
→ AI 빌더 그룹 명의로 발행해서 유입을 만들고, "우리는 바이브 코딩을 정말 잘한다"는 세일즈로 연결.

### 3.4 유튜브 / UTM

- 이솝 님 유튜브를 콘텐츠 탭으로 별도 분리할지, Insight 하위로 둘지 검토 필요. 유튜브가 핵심 채널이므로 별도 상위 탭 분리안도 검토 가치가 있다고 언급됨.
- UTM 설정해서 유튜브 스튜디오에서 유입 경로 확인 → "인사이트 탭에서 실제로 몇 명이 유튜브로 전환됐는지" 측정.

### 3.5 빌더 프로필 & 자산화

```
Work(프로젝트) → 참여 빌더 표시 → 빌더 클릭
   → 빌더 프로필 페이지 (참여 프로젝트 / 작성 콘텐츠 / 일하는 방식 한 줄 요약)
   → 이 프로필이 곧 "이력서"로 쓰임
```

- 참고 선례: 똑빌더(똑똑한 개발자 내부 시스템)의 "자산화" 기능. PDF 다운로드하면 프로젝트 이력·경력·학교·연차가 출력됨.
- 용도: ① 대기업 클라이언트에 제출할 이력서 ② 클라이언트가 "잘 모르겠고 추천해주세요"라고 할 때 담당자 조회 → AI가 프로젝트 이력 기반으로 협력사 중 가장 적합한 곳을 추천
- ⚠️ **리스크**: "지금 빌더 스쿨로 들어오신 분들은 포트폴리오가 없을 거잖아요. 그럼 AI 추천하면 후순위로 갈 확률이 매우 높다." → 기능이 아니라 **이 리스크를 해소하기 위해** 빌더 프로필·프로젝트 이력을 쌓는 구조가 사업적으로 필요함.
- 아이디어 수준으로만 공유된 상태라 이번 3주 범위에 포함되는지는 **아직 미정**. IA만 설계해두고 기능 개발은 백로그로 넘기는 방안이 합리적이나 확정은 필요함(§12 Q8).

## 4. 문의하기 & pluug 연동

```
문의하기 폼(pluug 폼) → 리드 적재 → 영업사원이 직접 배정 → 수주
```

- pluug = 영업 관리 툴(CRM).
- 왜 자동 매칭이 아니라 영업사원이 붙어야 하나? → 외주는 고단가라서 일반적인 자동 매칭으로는 성사되지 않기 때문. 사람이 직접 붙어야 함.
- 참고할 구현 사례: 똑똑한 개발자 사이트가 이미 이 방식으로 pluug와 연동돼 있음.
- ⚠️ 미확인: pluug 폼 연동이 API 방식인지, 임베드인지, 리다이렉트인지 기술 스펙 확인 필요. 계정·API 키를 누가 제공하는지도 미확인. 똑똑한 개발자 사이트 분석 + 별도 질의 필요.

## 5. 관리자 페이지 범위

조유리 질문("매칭 기능까지 포함되어야 하나요?")에 대한 답변으로 범위가 확정됨.

**포함 안 되는 것**
- ❌ 매칭 기능 (개발자 자동 매칭 같은 기능 없음)
- ❌ 리드/CRM 기능 (리드는 pluug가 전담, 우리 DB에는 콘텐츠만 저장)

**포함되는 것**
- ✅ 블로그 관리 (Insight 콘텐츠)
- ✅ 유저(빌더) 관리 — 개별 바이브 코더·빌더 계정. 빌더가 로그인해서 자신의 프로젝트를 업로드하면 최종 관리자가 승인
- ✅ 콘텐츠 관리 (포트폴리오 + 인사이트)

### 🆕 5.1 관리자 계정 · 등급 · 권한 체계 (2026-08-13, 관리자 목업 반영)

관리자 화면 시안(`artifact/admin`)에서 아래 기능을 신규로 제안했다. 클라이언트 확인 전까지는 시안이며, §14 Q10(관리자 권한 구분)에 대한 답으로 검토 중이다.

- 관리자 계정 생성(초대 방식) 및 등급(예: 최종 관리자 / 콘텐츠 관리자 / 검수 담당) 부여
- 등급별 메뉴 접근 권한(대시보드/Builder/Work/Work Process/Insight/설정/계정·권한) 매트릭스 관리
- 빌더 로그인 후 사용 가능한 메뉴를 빌더별로 개별 부여 — 예: Insight 글쓰기·수정·삭제 권한을 관리자가 켜고 끌 수 있음(삭제는 기본 비활성)
- 빌더가 업로드한 Work·Insight는 등급·권한과 무관하게 항상 승인/검수 대기 상태로 등록되며, 공개(발행) 전환은 최종 관리자 권한이 있어야만 가능(하드 룰 2와 동일한 원칙 적용)
- 관리자 로그인 화면 + 현재 로그인한 관리자 표시 + 비밀번호 변경 기능(§18 갱신, PRD FR-10)

## 6. 소구점 & 차별화 전략

**가장 중요한 원칙**: 첫 화면에서 "여기는 이런 곳이구나"가 즉시 전달돼야 합니다. 3사(똑똑한 개발자·이솝·크몽) 소개는 필요 없습니다. 교육 플랫폼 홍보가 아니라, "바이브 코딩으로 왜 우리를 선택해야 하는가"가 핵심입니다.

| 구분 | 일반적인 에이전시 | AI 빌더 그룹의 전략 |
| --- | --- | --- |
| 핵심 소구점 | 포트폴리오(개수·화려함) | 일하는 방식(AI 최적화 프로세스) + 검증된 맞춤 개발자 매칭 |
| 품질 우려 대응 | 저가형 반값 외주 → "싼 게 비지떡" | 체계적인 똑빌더 시스템으로 상향 평준화 |
| 인재 검증 | 경험 위주, 허위 포트폴리오 다수 | 우수 수료생 선별 배정 + 미달자 전액 환불 (※ 실제 적용은 2기부터 — §2.4 참조) |
| 장기 비전 | 일회성 매칭 후 끝 | 우수 빌더를 똑똑한 개발자 내부 조직으로 흡수 |

**"일하는 방식"으로 소구점을 옮긴 이유**

- "앱 개발"로 검색하면 나오는 개발사들은 각각 소구점이 다름(예: 디펙트럼 — 턴키 개발, AI 상담, 빠른 견적, 자체 서비스 포트폴리오 중심).
- 대부분의 에이전시는 포트폴리오를 강조하지만, 우리에게는 강조할 포트폴리오가 없음.
- 그래서 소구점을 바꿈: "AI 시대에는 AI에 최적화된 인재가 필요하다." 같은 개발자라도 잘하는 사람과 못하는 사람이 있다(자사 외주에도 컴플레인이 나오는 개발자가 있다는 솔직한 인정). 우리는 잘하는 개발자를 검증·검수하고 장기적으로 함께할 환경을 만든다. **"개발사를 고르는 게 아니라, 당신의 서비스에 맞는 개발자를 맞춤 매칭해 드린다."**

> "대부분의 에이전시들은 포트폴리오를 강조해서 설명하고 있어요. 근데 저희는 강조할 포트폴리오가 없잖아요. 그럼 우리의 소구점은 일하는 방식으로 하면 될 것 같거든요. AI 시대에는 AI에 최적화된 인재가 필요하다." (원문 인용)

## 8. 디자인 퀄리티 기준 (이번 프로젝트에서 가장 중요한 요구사항)

### 8.1 "딸깍 느낌" 절대 금지

> "가장 중요한 건 이 디자인 퀄리티가 절대 바이브 코딩으로 딸깍하고 만든 느낌이 나면 안 돼요."

주관적 기준이라 발주 담당자가 자신의 판단 근거를 직접 분석해 제시함. 핵심은 **섹션마다 인터랙션이 달라야 한다**는 것.

| ✅ 이렇게 (참고: 똑똑한 개발자 사이트) | ❌ 이러면 탈락 (반례: Ten AI) |
| --- | --- |
| Fade-in(아래→위) / 마우스 호버 시 반응 / 콘텐츠 Fixed+스크롤 연동 / 화면 전환 시 퍼지는 애니메이션 — 섹션마다 다르게 | 모든 섹션, 모든 텍스트, 모든 컴포넌트가 똑같은 "아래→위" 애니메이션만 반복 |
| 텍스트가 슬라이드되지 않는, 일부러 애니메이션을 안 넣은 영역도 둠 (강약 조절 자체가 판단 기준) | 전부 다 움직임 |

> "인터랙션이 섹션마다 다른 인터랙션을 보여줘요. (…) 여기서는 애니메이션이 없잖아요. 실제로 텍스트가 슬라이드 되지 않으니까 그런 것들이 제가 느끼기에는 사람이 했다라고 느껴지거든요." (원문 인용)

시간을 들여 퀄리티를 올리면 다른 결과물이 나온다는 게 전제. 고객이 진입했을 때 "여기는 좀 다르네"라는 느낌을 줘야 함.

### 8.2 에셋(이미지) 정책

> "에셋의 퀄리티가 홈페이지의 퀄리티를 좌우한다."

회사 홈페이지는 사실상 텍스트 + 이미지뿐이라, 이미지 퀄리티가 떨어지면 사이트 퀄리티가 통째로 낮아짐.

진행 순서:
1. 클라이언트에게 먼저 에셋(사진 등)을 요청한다.
2. 받은 에셋의 퀄리티가 낮으면 우리가 리터칭해서 품질을 올린 후 사이트에 반영한다.
3. 목업을 제출할 때는 우리 기준 최고 퀄리티 이미지로 제공한다.
4. 클라이언트가 나중에 이미지를 직접 교체하고 싶어하면 "이 정도 무드는 유지해야 퀄리티가 유지된다"고 반드시 안내한다 — 클라이언트는 이 기준을 모르기 때문.

**레퍼런스는 클라이언트가 주는 게 아니라 우리가 픽하는 것**
- "클라이언트한테 레퍼런스 사이트 달라고 한 게 아니에요. 혜미 님이 제가 봤을 때 이런 레퍼런스 사이트는 좀 좋을 것 같은데요라고 해서 혜미 님이 픽 해서 드린 거예요." (혜미 님은 현재 다른 회사 홈페이지 건을 수행 중이며, 같은 성격의 레퍼런스를 우리 팀에도 전달 예정)
- 실제 외주에서 클라이언트 요구는 "이런 느낌으로 만들어주세요" 정도가 끝. "이런 느낌"이 구체적으로 뭔지 되묻고, 우리가 레퍼런스를 골라서 제안하는 것 자체가 우리의 실력.

### 8.3 컴포넌트/UX

- 에셋 말고 디자인 구조 자체가 좋은 사이트(예: 카드 디자인)도 참고 대상. 단순히 따라 만들지 말고, "이 UX가 정말 좋은가"를 스스로 검토해야 함(예: 헤더가 넓어지는 인터랙션이 정말 좋은 UX인지 등). 배경: 클라이언트 측 프론트엔드를 더 고도화하는 중이라 좋은 UX에 대한 고민이 필수.

## 9. SEO / 데이터 트래킹

### 9.1 URL 슬러그를 분기하는 이유는 SEO가 아니라 GA 트래킹

- 예: 똑똑한 개발자 사이트 FAQ는 옵션에 따라 URL이 바뀜(`/faq/aiax` ↔ `/faq/it`). 단순 화면 전환이 아니라 URL을 바꾸는 이유는 GA(구글 애널리틱스)로 추적하기 위함.
- 활용: 현재 AI/AX가 기본값인데 사용자가 계속 IT 개발을 클릭하면 메뉴 순서를 바꿔야 한다는 의사결정 근거가 됨. **목적은 하나: 전환율 개선을 위한 데이터 확보.**

### 9.2 실측 사례 — 버튼 하나가 전환을 죽인다

| 시점 | 상태 | 주간 문의 유입 |
| --- | --- | --- |
| 평시 | 정상 | 하루 약 3건 / 주 10~20건 |
| 변경 후 1주 | FAQ 옆에 "소개서 다운받기" 버튼 추가 | 0건 |
| 버튼 제거 후 | 원복 | 주 10~20건으로 회복 |

> "사람들이 문의하기를 안 누르고 소개서 다운받고 끝나버리는 거예요. (…) 그 버튼을 없애버렸어요. 없애버리니까 (…) 다시 10건에서 20건 들어오고 있거든요." (원문 인용)

**교훈**: 버튼 하나가 전환을 크게 떨어뜨릴 수 있음. 요소 단위로 클릭 트래킹이 가능한 형태로 설계해야 함.

### 9.3 SEO 범위는 넓히지 않는다

한도균 질문("SEO/GEO/AEO 중 특별히 더 노출이 잘 되는 플랫폼이 있나요?")에 대한 답변:

- "기본적으로 SEO만 잘 되면 된다. GEO는 따라온다. 그것까지 보실 필요는 없다. 테크니컬적인 세팅만 해주면 된다." → **범위는 테크니컬 세팅까지.** 3주 일정에서 스스로 범위를 늘리지 않는다.
- 대상: 구글 + 네이버 기본.
- 단, 테크니컬 세팅이 완벽해도 콘텐츠를 AI로 대충 계속 찍어내면 결국 저품질로 떨어짐. 콘텐츠 품질은 작성자 역량에 달려 있음(콘텐츠 운영 주체가 유념할 사항이며, 이번 구축 범위는 아님).

## 10. 협업 방식

### 10.1 목업 제출 규칙 (다음 미팅 숙제)

```
각자 개인별 제작 → 팀장 2인이 판단 → 베스트 1~2개 픽 → 탈락 사유 문서화 → 전체 제출
```

- 탈락한 시안도 버리지 않고 이유와 함께 같이 제출.

### 10.2 의사결정 원칙

| 규칙 | 취지 |
| --- | --- |
| 투표 금지 | "가장 워스트는 투표를 하는 것. 최악입니다." |
| 총대는 한 명(수행팀 2인)이 멘다 | "최종 결정은 저희 둘이서 하겠습니다"를 명시적으로 선언 |
| 탈락자를 굳이 납득시킬 필요 없음 | "그래서 팀장과 팀원이 존재하는 것" |

### 10.3 팀 협업 전제

- 프리랜서의 궁극적 목표는 혼자 일하는 것이지만, 지금은 디자인·프론트/백엔드 서포트가 필요해서 팀으로 감.
- **월 400만 원 벌 때까지는 무조건 팀 단위**, 정산은 N빵(균등 분배)이 기본 전제.
- 수행팀에 요청된 관찰 항목: 협업이 어려운 팀원이 있는지 체크할 것. 협업이 어려운 사람도 어떻게 잘 이끌어갈지가 중요. 클라이언트 소통 능력도 평가 대상.

### 10.4 커뮤니케이션 규칙

- 단체방 1개로 통합 (당초 A팀/B팀, 내부/외부 분리를 고려했으나 최종적으로 "그냥 방 하나만 만들게요"로 정리됨, 34:42). 발주 담당자가 개설해 초대.
- ⚠️ **채널 종류는 자료 간 표기가 다릅니다.** 회의록 본문(§8.4)은 "슬랙방"이라 하고, 결정사항 표(D9)는 "카카오톡 단체방"이라 적혀 있어 **원문 자체에 불일치가 있습니다.** 다음 미팅에서 실제 채널(슬랙 vs 카카오톡)을 재확인 필요.
- 그날 나온 내용은 방에 기록. 질문은 모아서 한 번에 전달. 답변이 없으면 전화로 재촉("진짜 그렇게 해 주셔야 돼요"). 슬랙 등 다른 채널로도 추가 소통 가능.

### 10.5 정산

- 팀장이 더 많은 베네핏, 나머지는 N빵.
- 포인트(역할·기여도)마다 단가가 다름.
- 1,000만 원/2,000만 원 기준 배분안은 발주 담당자가 정리해 공유하기로 함 (아직 미공유 — 실제 프로젝트 배정 시 그 기준으로 설명하는 편이 이해가 빠를 것이라 함).
- 조유리가 "팀원들이 정산에 관심이 많다"고 요청해 문서화 약속을 받음.

## 17. 🆕 2차 미팅 반영 (2026-08-12)

> 아래는 2026-08-12(수) 2차 미팅(`260812 2차 미팅.txt`, 클로바노트 전사본) 내용을 반영해 새로 추가한 내용이다. 1차 미팅에서 약속한 A1(개인별 목업 제작 → 베스트 1~2개 픽)에 대한 리뷰 미팅이었다.

### 17.1 목업 리뷰 결과

- 제출된 여러 시안 중 **2개를 최종 선정**했다(A1 완료).
  - **1안(베스트)**: 인터랙션(호버 시 정지 등) 퀄리티가 가장 높고, 브랜드 네임을 활용해 공신력·안정성을 잘 표현함. 소구점이 가장 잘 드러났다는 평가. 카피가 AI스럽지 않고 자연스러우며, 페이지 특성에 맞는 포맷을 사용. 콘텐츠(Insight) 영역이 특히 트렌디하다는 평가를 받음.
  - **2안**: 에셋 퀄리티가 가장 높음. **교육 콘텐츠를 위한 별도 페이지**를 따로 만들어 제공함 — PRD v2(§4 FR-9, §10 #5)에 반영된 **Eduinfo 섹션**과 같은 방향의 시안으로 확인된다.
- ⚠️ **공통 피드백(추가 개발 필요)**: 랜딩 페이지는 두 시안 모두 좋다는 평가지만, **상세 페이지로 들어갔을 때 컴포넌트들이 AI스러운 느낌이 남아있다**는 지적을 받았다. 다음 단계에서 상세 페이지 컴포넌트 고도화가 필요하다.
- 다음 단계는 **2개 시안을 조합·발전**시키는 방향이며, 최종적으로는 **1개 시안으로 통합**해 전체를 고도화하기로 했다("시안 중 하나나, 최종 시안을 하나 만들어서 그거를 기반으로 다 고도화").
- 🆕 신규 액션(A15): 선정되지 않은 시안을 포함해 "누가 어떤 시안을 만들었는지" 전체를 노션 등으로 리스트업해 공유해야 한다.

### 17.2 기술 스택 · 인프라 확정

| 항목 | 결정 내용 |
| --- | --- |
| 프레임워크 | **Next.js + Supabase** 연동으로 진행 |
| Supabase 계정 | 우선 팀별로 각자 **개인 무료(Free) 프로젝트**로 연동 작업 진행(예: "빌더그룹 팀1"). 최종 컨펌된 페이지만 나중에 클라이언트의 정식(유료) Supabase 프로젝트로 이관. 클라이언트가 유료 프로젝트를 만들어 팀장(조유리·도희)에게 오너 권한을 이미 부여함(회의 중 처리) |

### 17.3 협업 체계 — 팀 세분화

- 선정된 2개 시안을 기반으로 **총 6명이 각자 개발(디벨롭)을 진행하고 백엔드까지 연결**한다.
- 인원은 **3인/3인** 또는 **3인/4인** 구성으로 나뉠 예정.
- 팀 밸런스를 위해 **디자인 퀄리티가 좋은 사람과 백오피스(관리자) 설계를 잘하는 사람을 같은 팀에 배치**한다.
- 기존 팀 구성 외에 다른 팀원과 함께하고 싶다는 의견이 있으면 사전에 자유롭게 제시할 수 있다.
- 지금은 팀 리더가 클라이언트와의 메인 커뮤니케이션을 담당하지만, 팀이 확정되면 이후 **개별 팀 단위 커뮤니케이션**으로 전환될 예정이다.

### 17.4 다음 단계 평가 기준

- 다음 미팅까지 목표: **프론트엔드 화면(앞단) 최종 마무리** + **백오피스(관리자 페이지) 설계 완료**.
- 프론트는 "시안 중 하나(또는 통합한 최종 시안)"를 기준으로 계속 고도화하면서, 백엔드 설계를 병행해도 된다는 것이 클라이언트 답변.

### 17.5 영업 · 협업 참고 사항 (실무 참고용, 요구사항 아님)

- 실제 외주에서는 클라이언트가 제시하는 레퍼런스에 맞추되 **그대로 베끼지 않는 것**이 중요하다는 조언 — 그대로 베끼면 차별화가 사라짐.
- 인성·커뮤니케이션 문제가 있는 클라이언트는 사전에 거르는 편이 낫다는 경험 공유(고액 프로젝트 1건보다 소액 다건이 스트레스가 적다는 판단 기준).
- 외주는 도메인 지식이 없는 상태로 영업을 시작해도 진행하며 학습해 나가는 경우가 많다는 현실적 조언(예: IoT·항공권 예약 시스템(OTA 연동) 사례).
- **2026년 8월 중 팀원 전원이 실제 외주 프로젝트에 투입될 예정**이라는 일정이 공유됨.
