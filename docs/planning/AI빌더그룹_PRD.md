## 1. 개요 & 목적

**제품**: AI 빌더 그룹(가제)의 영업용 웹사이트 — 랜딩 페이지 + 관리자 페이지.

**문제**: 신규 브랜드라 내세울 포트폴리오가 없고, "마케팅비가 매출의 40% 이상을 먹는" 기존 교육 플랫폼 구조와는 다른 방식으로 신뢰를 얻어야 한다. 실측 사례상 CTA 버튼 하나 때문에 주간 문의가 10~20건에서 0건까지 떨어진 적이 있어(기획서 §9.2), 트래킹 없이는 무엇이 전환을 죽이는지 알 수 없다. 그리고 "바이브 코딩으로 대충 찍어낸 느낌"이 조금이라도 나면, 정작 "바이브 코딩 외주를 믿고 맡기라"는 메시지 자체가 무너진다.

**목적**: 첫 화면에서 "여기는 바이브 코딩으로 외주를 받아주는 곳"임을 즉시 전달하고, 문의(리드)를 pluug(CRM)로 정확히 넘겨 실제 수주로 연결한다. 동시에 Work(포트폴리오)·Insight(콘텐츠)·빌더 프로필을 통해 포트폴리오 부재를 신뢰 자산으로 상쇄한다.

**핵심 가치 제안**: "포트폴리오 개수가 아니라, 일하는 방식과 검증된 맞춤 개발자 매칭." 저가 소구("반반외주"식 실패 사례, 기획서 §2.5) 대신 똑빌더 시스템 기반의 체계성으로 품질을 보증한다.

**핵심 성공 조건 (기획서 원문 기준, 이 PRD 전체를 관통하는 두 축)**
1. 딸깍(AI로 대충 찍어낸) 느낌이 나지 않는 디자인
2. 전환을 추적할 수 있는 트래킹 구조

**타겟**
- 1차: 바이브 코딩 외주를 맡기고 싶은 스타트업/중소기업 프로젝트 발주 담당자
- 2차: 향후 프로필을 이력서처럼 쓰게 될 빌더(수료생) — 대기업 클라이언트 제출용, AI 추천 매칭용

## 3. 범위 (Scope)

### In Scope (v1 / 3주)

- **홈**: 3사 소개 없이 "바이브 코딩 외주" 메시지를 즉시 전달하는 첫 화면
- **Work(포트폴리오)**: 실제 수행 프로젝트 + 참여 빌더 연결(목업 기준: 카드 클릭 시 빌더 상세 프로필을 모달로 노출 — §10 #6)
- **Insight(콘텐츠/블로그)**: 빌더 작성 글 → 빌더 프로필 연결. 유튜브 강의 콘텐츠는 별도 **Eduinfo** 섹션으로 분리했다(A5 결정 반영 — §10 #4)
- 🆕 **Eduinfo(교육 콘텐츠)**: 이솝 강의 영상 + PDF 자료 인덱스(PRD v1에는 없던 섹션, 목업 단계에서 추가됨 — §4 FR-9, §10 #5)
- **문의하기**: pluug 폼 연동으로 리드 적재(목업 기준: 이름/회사/연락처/프로젝트 유형/메모 필드의 모달형 문의 폼 — §10 #9)
- **관리자 페이지**: 블로그(Insight) 관리, 유저(빌더) 계정 관리, 빌더 업로드 프로젝트 승인
- **GA 트래킹**: URL 슬러그 분기, 요소 단위 클릭 이벤트, UTM
- **SEO 테크니컬 세팅**: 구글 + 네이버 기본
- **디자인 품질 게이트**: 섹션별 차별화된 인터랙션, 고퀄리티 에셋(§8) — 목업에서 히어로 틸트/자동 언폴드, Work 빌더 스포트라이트 로테이션, Insight 카드 호버 정지, FAQ 아코디언, Related 랜덤 라이트업 등으로 실증됨(§10 #13)

| 항목 | 결정 근거 |

| 3사(크몽·똑똑한 개발자·이솝 님) 소개 페이지 | D1 — 교육 플랫폼 홍보가 목적이 아님 |

## 4. 기능 요구사항

기능 영역별로 유저스토리 + 수용기준(Given/When/Then) + 관련 기획서 절을 정의한다. 문의하기(FR-4)와 홈 첫인상(FR-1)이 "핵심 성공 조건 두 가지"와 직결되므로 가장 촘촘히 정의한다.

### FR-1 · 홈 · 첫 메시지 전달 (§3.1, §6)

- **US-1.1** 잠재 고객으로서, 사이트에 들어오자마자 "바이브 코딩으로 외주를 맡기는 곳"임을 바로 알고 싶다.
- **US-1.2** 잠재 고객으로서, 3사(크몽·똑개·이솝)의 복잡한 관계를 몰라도 서비스를 이해하고 싶다.

- **AC-1.1** Given 신규 방문자, When 홈 첫 화면(above the fold)을 로드, Then 3사 소개 없이 "바이브 코딩으로 외주를 받는다"는 핵심 메시지가 즉시 노출된다.
- **AC-1.2** Given 홈 스크롤, When 섹션이 전환, Then 섹션마다 서로 다른 인터랙션(fade-in, hover 반응, fixed+스크롤 연동 등)이 적용되고, 일부 섹션은 의도적으로 애니메이션을 넣지 않는다(§8.1 강약 조절 = 딸깍 방지의 핵심 판단 기준).
- **AC-1.3** Given 홈 CTA, When 사용자가 "문의하기" 또는 "Work 보기"를 클릭, Then 각각 FR-4·FR-2로 이동하고 클릭 이벤트가 GA로 전송된다(FR-8).
- **AC-1.4** Given 소구점 카피, When 어떤 문구든 노출, Then "저렴함"을 소구하지 않고 "일하는 방식 + 검증된 매칭"을 소구한다(§2.5, D5).
- **AC-1.5** 🆕 Given 목업 반영(2026-08-12), When Hero CTA 역할을 재검토, Then 1차 CTA는 "VIEW WORK PORTFOLIO"(Work 섹션 이동)로, "프로젝트 문의하기"는 상단 nav와 프로젝트 상세 모달의 상시 노출 CTA로 재배치됐다. AC-1.3의 "문의하기/Work 보기 클릭 시 각각 FR-4·FR-2로 이동" 요건은 진입점만 재배치됐을 뿐 동일하게 충족된다(§10 #8).

### FR-2 · Work(포트폴리오) (§3.2)

- **US-2.1** 잠재 고객으로서, 실제로 수행한 프로젝트만 보고 신뢰를 판단하고 싶다.
- **US-2.2** 잠재 고객으로서, 프로젝트에 참여한 빌더가 누구인지 보고 그 사람을 더 알고 싶다.

- **AC-2.1** Given Work 목록, When 프로젝트 카드가 렌더, Then 실제 수행 프로젝트만 노출되며 목업/가상 사례는 포함하지 않는다(§7.2 목업 포트폴리오 양산 업체 반면교사).
- **AC-2.2** Given 프로젝트 상세, When 참여 빌더 영역을 클릭, Then 해당 빌더 프로필 페이지(FR-7)로 이동한다(§3.5).
- **AC-2.3** Given 오픈 시점 콘텐츠 소스 미확정(Q4 — 똑똑한 개발자 실적 전용 가능 여부), When 런칭 시점까지 확정되지 않으면, Then Work 섹션을 "준비 중" 빈 상태로 노출할 수 있도록 설계한다(콘텐츠 0건이 배포 블로커가 되지 않게).
- **AC-2.4** 🆕 Given 목업(2026-08-12), When Work 카드를 클릭, Then 별도 페이지 대신 해당 프로젝트를 만든 빌더의 상세 프로필(경력·프로젝트 수·위치·상태·작업 방식 요약·포트폴리오 갤러리 12건)이 모달로 노출된다 — FR-7(빌더 프로필)의 상당 부분이 별도 페이지가 아니라 이 모달 패턴에 흡수된 형태다. FR-7을 이 모달로 대체할지, 별도 프로필 페이지를 병행할지 재확인 필요(신규 Q17, §10 #6).
- **AC-2.5** 🆕 Given 목업의 프로젝트 카드·빌더 정보, When 콘텐츠를 확인, Then 현재는 전부 샘플/플레이스홀더 데이터다(이름·경력·프로젝트 수 등 실제 값 아님) — AC-2.1(실제 수행 프로젝트만 노출)은 아직 충족되지 않았고 M2 콘텐츠 확정 시 실데이터로 교체가 필요하다(§10 #7).
- **AC-2.6** 🆕 Given 2차 미팅(2026-08-12) 피드백, When 상세 화면(예: Work 포트폴리오 모달, AC-2.4)을 검토, Then 랜딩 첫인상은 두 후보 시안 모두 합격점을 받았으나 **상세 페이지로 진입했을 때 컴포넌트가 AI스러운 느낌이 남아있다**는 지적을 받았다 — 다음 단계에서 상세 컴포넌트 전반의 추가 고도화가 필요하다(신규 Q19, §11 #7).

### FR-3 · Insight(콘텐츠/블로그) + 유튜브 연계 (§3.3, §3.4)

- **US-3.1** 마케팅 담당자로서, 카테고리별로 콘텐츠를 발행해 유입을 만들고 싶다.
- **US-3.2** 방문자로서, 빌더가 쓴 글에서 그 빌더의 프로필로 이동하고 싶다.

- **AC-3.1** Given Insight 목록, When 카테고리 필터를 적용, Then "일하는 방식(업무 프로세스) / AI 활용 공유회 / 빌더가 쓴 글" 등 우리 핏에 맞게 재구성된 카테고리로 필터링된다(A4).
- **AC-3.2** Given 빌더가 작성한 글, When 작성자 영역을 클릭, Then 해당 빌더 프로필(FR-7)로 이동한다.
- **AC-3.3** Given Insight 내 유튜브 링크, When 사용자가 클릭, Then UTM 파라미터가 부여되어 있어 유튜브 스튜디오에서 유입 전환을 추적할 수 있다(§3.4).
- **AC-3.4** Given 유튜브 탭 배치가 미확정(A5 — Insight 하위 vs 별도 상위 탭), When IA를 설계, Then 두 배치안을 모두 수용 가능한 구조로 설계하고 최종 배치는 목업 리뷰에서 확정한다.
- **AC-3.5** 🆕 Given A5 결정, When 목업을 반영, Then 유튜브 강의 콘텐츠는 Insight 하위가 아니라 완전히 분리된 **Eduinfo** 섹션(FR-9)으로 배치됐다 — Insight는 블로그형 아티클(목업 기준 카드 6건, 클릭 시 모달 상세)만 다룬다(§10 #4).
- **AC-3.6** 🆕 Given 목업의 Insight 상세 노출 방식, When 실제 서비스로 퍼블리싱, Then 현재의 모달(다이얼로그) UI는 고유 URL이 없어 검색엔진이 색인할 수 없다 — FR-8 AC-8.3(SEO 기본 세팅)과 상충할 수 있으므로, 실제 구현 시 개별 글마다 라우팅된 정적 페이지를 두고 모달은 프리뷰 용도로만 남길지 결정해야 한다(신규 Q15).

### FR-4 · 문의하기 · pluug 연동 (§4) ⭐ 핵심

- **US-4.1** 잠재 고객으로서, 프로젝트 의뢰를 폼으로 남기고 싶다.
- **US-4.2** 영업 담당자로서, 리드가 pluug(CRM)에 자동 적재되어 사람이 직접 배정받고 싶다(고단가 외주는 자동 매칭으로 성사되지 않기 때문).

- **AC-4.1** Given 문의하기 폼, When 필수 항목(연락처 등) 입력 후 제출, Then 리드가 pluug로 전달되고 사용자에게 제출 완료 화면/메시지가 노출된다.
- **AC-4.2** Given pluug 연동 방식(API / 임베드 / 리다이렉트)이 미확정(Q7), When 개발에 착수, Then 똑똑한 개발자 사이트의 기존 연동 사례를 기술 분석해 방식과 계정·API 키 제공 주체를 먼저 확정한 뒤 구현한다.
- **AC-4.3** Given 문의 전환을 잠식할 수 있는 다른 CTA(예: "소개서 다운받기"), When 페이지에 신규 요소를 배치할지 결정, Then 배치 전후 GA 전환 추이를 비교해 검증한다(§9.2 실측 사례 — 버튼 하나로 주 10~20건→0건까지 떨어진 전례가 있음).
- **AC-4.4** Given 폼 제출, When 완료, Then 제출 이벤트가 GA로 전송되어 전환율을 측정할 수 있다(FR-8과 연동).
- **AC-4.5** 🆕 Given 목업(2026-08-12)의 문의 폼, When 진입 경로를 확인, Then 상단 nav의 "프로젝트 문의하기"와 Work 카드 상세 모달의 "프로젝트 문의하기" 버튼 두 곳에서 동일한 모달형 폼(이름·회사·연락처·프로젝트 유형 select·메모)이 열린다. 제출 시 현재는 클라이언트 측 성공 메시지만 노출하며, pluug 실연동(Q7)은 아직 미구현이다(§10 #9).
- **AC-4.6** 🆕 Given 2차 미팅(2026-08-12) 결정, When pluug 연동 방식을 확정, Then 우선 임의 pluug 계정으로 폼을 연동해두고, 관리자 페이지(FR-5)에서 폼 링크(URL)를 교체하면 공개 사이트에 그대로 반영되도록 구현한다 — 정식 pluug 프로덕션 계정 연동은 클라이언트가 추후 처리한다. API/임베드/리다이렉트 중 정확한 최종 연동 방식은 여전히 미확정이다(Q7, §11 #2).

### FR-5 · 관리자 · 블로그(Insight) 관리 (§5)

- **US-5.1** 콘텐츠 관리자로서, Insight 글을 작성·수정·발행하고 카테고리를 지정하고 싶다.

- **AC-5.1** Given 관리자 로그인, When 블로그 관리 화면에 진입, Then 글 목록/작성/수정/카테고리 지정 기능을 사용할 수 있다.
- **AC-5.2** Given 매칭 기능·리드 관리 요구, When 관리자 화면을 설계, Then 해당 기능은 포함하지 않는다(D3 — 매칭·CRM은 pluug가 전담, 우리 DB에는 콘텐츠만 저장).
- **AC-5.3** 🆕 Given AC-4.6의 pluug 연동 방향(2차 미팅, 2026-08-12), When 관리자 화면을 설계, Then 문의 폼 링크(pluug URL)를 조회·수정할 수 있는 설정 필드를 포함한다 — 관리자에서 링크를 바꾸면 공개 사이트의 문의하기 진입점(FR-4)이 즉시 그 링크를 반영해야 한다(§11 #3).

### FR-6 · 관리자 · 유저(빌더) 관리 + 프로젝트 승인 (§5)

- **US-6.1** 빌더로서, 로그인해 내가 수행한 프로젝트를 업로드하고 싶다.
- **US-6.2** 최종 관리자로서, 빌더가 업로드한 프로젝트를 승인해야만 공개되게 하고 싶다.

- **AC-6.1** Given 빌더 계정 로그인, When 프로젝트를 업로드, Then 상태가 "승인 대기"로 등록되고 Work(FR-2)에는 즉시 노출되지 않는다.
- **AC-6.2** Given 승인 대기 프로젝트, When 최종 관리자가 승인, Then 상태가 "공개"로 전환되어 Work 목록에 노출된다.
- **AC-6.3** Given 빌더 계정 목록, When 관리자가 조회, Then 계정 활성/비활성 상태를 확인·변경할 수 있다.
- **AC-6.4** 🆕 Given 관리자 목업(2026-08-13, `artifact/admin`)의 "빌더 로그인 권한" 화면, When 관리자가 빌더별 권한을 설정, Then 빌더는 로그인 후 부여받은 메뉴만 사용할 수 있다 — 기본값은 "본인 Work 업로드"만 허용이며, Insight 글쓰기·수정·삭제는 관리자가 빌더별로 개별 켜고 끌 수 있다(삭제는 기본 비활성). 빌더가 업로드한 Work·Insight는 권한과 무관하게 항상 승인/검수 대기로 등록되고, 공개(발행) 전환은 최종 관리자만 가능하다(§12 #2).

### FR-7 · 빌더 프로필 (IA 설계, 기능은 백로그) (§3.5)

- **US-7.1** 방문자/클라이언트로서, 빌더의 참여 프로젝트·작성 콘텐츠·일하는 방식 한 줄 요약을 한 페이지에서 보고 싶다.

- **AC-7.1** Given 빌더 프로필 IA, When 설계 산출물을 제출, Then 참여 프로젝트 목록·작성 콘텐츠 목록·일하는 방식 한 줄 요약 영역을 포함한 와이어프레임을 제공한다.
- **AC-7.2** Given 3주 범위 확정 전(Q8), When 개발 착수 여부를 결정, Then IA·와이어프레임까지만 v1에 포함하고 실제 기능(자산화 PDF, AI 추천 매칭 등)은 백로그로 분리한다.
- **AC-7.3** Given 빌더 프로필의 사업적 목적("포트폴리오 없는 신규 빌더가 AI 추천에서 후순위로 밀리는" 리스크, §3.5), When IA를 설계, Then 이 리스크를 인지한 상태로 화면 구조를 잡는다(당장 기능 구현 여부와 무관하게).

### FR-8 · SEO · GA 트래킹 (§9)

- **US-8.1** 마케팅 담당자로서, 어떤 버튼/메뉴가 전환에 기여하는지 데이터로 확인하고 싶다.

- **AC-8.1** Given 옵션에 따라 화면이 전환되는 UI(예: FAQ), When 사용자가 옵션을 클릭, Then 단순 화면 전환이 아니라 URL 슬러그가 바뀌어 GA로 유입 경로를 구분 추적할 수 있다(§9.1 예: `/faq/aiax` ↔ `/faq/it`).
- **AC-8.2** Given 주요 CTA 버튼, When 렌더링, Then 요소 단위 클릭 이벤트가 GA에 태깅되어 있다.
- **AC-8.3** Given 검색엔진 노출, When 테크니컬 SEO 세팅을 적용, Then 구글·네이버 기준 메타태그/사이트맵/소유확인 등 기본 세팅이 완료된다(GEO/AEO 별도 대응 없음, D10).
- **AC-8.4** 🆕 Given 목업의 FAQ 구현, When 확인, Then 현재는 카테고리 구분 없는 5문항 아코디언(단일 오픈)으로만 구현되어 있어 AC-8.1의 슬러그 분기(`/faq/aiax` ↔ `/faq/it`)는 아직 반영되지 않았다 — 실제 개발(M2) 시 카테고리 분기 설계가 필요하다(신규 Q16, §10 #12).

### FR-9 · Eduinfo · 교육 콘텐츠 🆕 (목업 단계에서 신규 추가 — PRD v1에는 없던 기능, §10 #5)

- **US-9.1** 방문자로서, 이솝님의 강의 영상과 자료를 보고 직접 만들어볼 수 있는 힘을 기르고 싶다.
- **US-9.2** 마케팅 담당자로서, 교육 콘텐츠를 통해 유튜브 채널 유입과 브랜드 신뢰를 함께 쌓고 싶다.

- **AC-9.1** Given Eduinfo 진입, When 섹션을 로드, Then 강의 목록(목업 기준 10편) · 선택된 강의의 유튜브 임베드 플레이어 · 관련 PDF 자료 요약이 한 화면에 노출된다.
- **AC-9.2** Given 강의 목록에서 항목 선택, When 클릭, Then 임베드 플레이어와 PDF 요약이 함께 갱신되고, 유튜브 원본 채널로 이동하는 새 탭이 전환 애니메이션과 함께 열린다.
- **AC-9.3** Given PDF 자료, When "PDF 자료 다운로드" 버튼 클릭, Then 현재 목업은 안내 문구만 노출한다(placeholder) — 실제 파일/스토리지 연동은 미구현이다(신규 Q13).
- **AC-9.4** Given 유튜브 채널 연동, When 공식 채널이 확정되면, Then 목업의 샘플 검색 링크(예: "이솝 바이브코딩")를 실제 채널 재생목록으로 교체한다 — 현재 채널 ID는 임시값이다(신규 Q14).

> IA 근거: FR-3(Insight)의 A5(유튜브 탭 배치) 오픈 이슈가 "완전히 분리된 상위 섹션"으로 해소된 형태다. §6 MoSCoW 재조정 필요.

### FR-10 · 관리자 계정 · 등급 · 권한 관리 🆕 (관리자 목업 단계에서 신규 제안 — PRD v3에는 없던 기능, §12 #1)

- **US-10.1** 최종 관리자로서, 팀원에게 관리자 계정을 발급하고 역할에 맞는 접근 범위만 부여하고 싶다.
- **US-10.2** 콘텐츠 관리자로서, 내 등급에 허용된 메뉴만 보이길 원한다 — 권한 밖의 화면·설정에 실수로 접근하고 싶지 않다.
- **US-10.3** 빌더로서, 로그인 후 내게 허용된 기능(예: Insight 글쓰기)만 사용하고 싶다.
- **US-10.4** 모든 관리자·빌더 계정 사용자로서, 지금 내가 어떤 계정으로 로그인했는지 항상 확인하고, 필요하면 비밀번호를 직접 바꾸고 싶다.

- **AC-10.1** Given 최종 관리자 로그인, When "계정 · 권한" 화면에 진입, Then 관리자 계정을 생성(초대 이메일 발송)하고 등급(예: 최종 관리자/콘텐츠 관리자/검수 담당)을 지정할 수 있다.
- **AC-10.2** Given 등급별 메뉴 접근 권한 매트릭스, When 최종 관리자가 값을 변경, Then 대시보드·Builder·Work·Work Process·Insight·설정·계정·권한 7개 메뉴 각각에 대해 전체/편집·승인/조회/접근불가 수준을 등급별로 설정할 수 있다.
- **AC-10.3** Given 빌더 로그인 권한 표, When 최종 관리자가 특정 빌더의 토글을 변경, Then 해당 빌더의 로그인 후 화면에 그 권한(본인 Work 업로드, Insight 작성/수정/삭제)만큼만 메뉴가 노출된다 — 삭제 권한 기본값은 비활성이다.
- **AC-10.4** 🆕 Given 로그인이 필요한 관리자·빌더 화면, When 사용자가 로그인, Then 전용 로그인 화면(이메일·비밀번호)을 통과해야 하며, 로그인 후에는 사이드바 등 상시 노출 영역에 **현재 로그인한 계정의 이름과 등급**이 항상 표시된다.
- **AC-10.5** 🆕 Given 로그인한 계정, When 사용자가 "계정 설정"에 진입, Then 본인 비밀번호를 변경할 수 있다 — 관리자 등급 사용자는 추가로 다른 계정의 비밀번호를 강제 초기화할 수 있다(§12 #4).
- **AC-10.6** Given 관리자·빌더 계정 전반, When 인증되지 않은 사용자가 접근, Then 어떤 등급의 화면에도 접근할 수 없다 — 단, 현재(2026-08-13 기준) apps/admin(:3001)은 실제 인증이 구현되지 않은 로컬 데모 상태이며, 이 FR은 인증 구현(WO-3, `docs/analysis/05-work-orders.md`)이 선행돼야 실효성이 생긴다.
- **AC-10.7** Given 등급 이름·개수와 메뉴별 세부 권한 범위, When 시안을 검토, Then 현재 값(최종 관리자/콘텐츠 관리자/검수 담당)은 예시이며 클라이언트 확인 후 확정한다(신규 Q21).

> IA 근거: PRD §8 Q10(개발자 선택 주체, 검수 담당·방식, 관리자 권한 구분)에 대한 구체 제안. `artifact/admin`의 "계정 · 권한" 화면 + 로그인 화면으로 시안화됨.
