## 1. 한 줄 정의와 성공 조건

> **AI 시대에 최적화된 고품질 바이브코딩 외주 전문 브랜드의, 수주용 랜딩 페이지 및 관리 운영 플랫폼**

🔒 **이것은 교육 플랫폼 홍보 사이트가 아니다.** 고객이 들어와 **개발을 의뢰하는** 사이트다. AI 빌더 스쿨(교육) **위에 얹는 상위 브랜드**의 사이트이며, 이번 건은 내부 연습 과제가 아니라 **실제 외주와 동일하게 진행·평가**된다.

### 1.1 성공 조건 — 두 개뿐이다

| # | 조건 | 판별 방법 | 실패하면 |
|---|---|---|---|
| **①** | **"AI로 딸깍해서 만든 느낌"이 나지 않는 디자인** | **섹션마다 다른 인터랙션** (§6.1) | 나머지가 다 좋아도 탈락 |
| **②** | **전환율을 개선할 수 있는 데이터 트래킹 구조** | URL 슬러그 분기 → GA4 / UTM / 요소 단위 이벤트 (§7) | 오픈 후 개선 판단 근거가 없음 |

> 원문: *"가장 중요한 거는 이 디자인의 퀄리티가 절대 바이브 코딩으로 딸깍으로 만든 느낌이 나면 안 돼요."* (16:55)

### 1.2 이 사이트가 존재하는 사업적 이유

```
[1차] 유료 커뮤니티  →  [2차] 교육  →  [3차] 일감 매칭·자생  →  [4] 인재 내재화
    (AI 네이티브)        (3트랙)        (크몽 영업조직)         (똑똑한 개발자)
                                            ↑
                                    ★ 이번 프로젝트가 담당하는 구간
```

- 3사 협업 구조: **똑똑한 개발자 · 이솝 님의 교육 회사 · 크몽**
- 이 사이트의 임무: **리드를 받아 크몽 영업 조직에 넘기고, 수료 빌더에게 매칭해 "월 400만 원 이상 버는 성공 사례"를 만든다.**
- 🔒 3사 소개 페이지는 **만들지 않는다** (D1). 교육 홍보가 목적이 아니므로.

## 2. 포지셔닝 — 무엇으로 이기는가

### 2.1 소구점 이동: 포트폴리오 → 일하는 방식

| 구분 | 일반적인 에이전시 | **AI 빌더 그룹** |
|---|---|---|
| 핵심 소구점 | 포트폴리오 개수·화려함 | **AI에 최적화된 일하는 방식 + 검증된 맞춤 개발자 매칭** |
| 품질 우려 대응 | 저가형 반값 외주 | **똑빌더 시스템 기반 상향 평준화**된 결과물 |
| 인재 검증 | 허위 포트폴리오 다수 | 선별 배정 + 미달자 정리로 인재 풀 관리 |
| 관계 | 일회성 매칭 후 종료 | 우수 빌더를 내부 조직·파트너로 흡수 |

> 원문: *"대부분의 에이전시들은 포트폴리오를 강조해요. 근데 저희는 강조할 포트폴리오가 없잖아요. 그럼 우리의 소구점은 일하는 방식으로 하면 될 것 같거든요. AI 시대에는 AI에 최적화된 인재가 필요하다."* (27:05)

### 2.2 카피 작성 시 금지·주의 사항 — **반드시 지킬 것**

| # | 규칙 | 근거 |
|---|---|---|
| **C1** | **가격·저렴함을 소구하지 않는다** | 스파르타 '반반외주' 실패의 원인이 가격 역설. *"500만 원으로 이상한 걸 만들 바에 1,000만 원 주고 더 좋은 걸 만들겠다"* |
| **C2** | **포트폴리오 "개수"를 자랑하지 않는다** | 강조할 포트폴리오가 아직 없고, 개수 경쟁 자체가 탈피 대상 |
| **C3** | 1기 운영 문구는 **"우리가 선별한 잘하는 분들 위주로만 진행한다"** | 실제 1기는 전원 동일 진행이지만 **사이트 문구는 선별 기준으로 간다** (클라이언트 명시) |
| **C4** | AX 컨설팅은 **문구에 넣지 않는다** | 🔒 이번 범위 제외 (D2). 서비스가 아직 없음 |
| **C5** | 근거 없는 수치(만족도 %, 누적 건수 등)를 **임의로 쓰지 않는다** | 자료 미수령 상태. 목업에서는 플레이스홀더 + 🟡 배지 |

### 2.3 첫 화면이 3초 안에 전달해야 하는 것

> *"결국에는 우리가 제공하는 서비스가 **바이브 코딩으로 외주를 해드립니다**가 첫 번째."* (25:36)

Hero에서 **① 무엇을 해주는 회사인지 ② 왜 우리여야 하는지** 두 문장 안에 끝난다. 3사 소개도, 교육 소개도 첫 화면에 없다.

### 4.2 슬러그(URL) 정책 🟡

**목적은 SEO이자 트래킹이다.** 슬러그는 확정 후 리다이렉트 없이 바꾸면 색인이 소멸하므로 **개발 착수 전에 확정**한다.

| 대상 | 규칙 | 예시 |
|---|---|---|
| Work 상세 | `업종·기술 + 프로젝트명` (한글 자연어 유지) | `/work/ai-챗봇-○○○` |
| Insight 상세 | `핵심 키워드 조합` | `/insight/바이브코딩-외주-고르는법` |
| Insight 카테고리 | 영문 소문자 | `/insight/how-we-work` |
| FAQ | **옵션별로 URL을 분기** (§7.2) | `/faq/vibe` ↔ `/faq/it` |
| 목록 필터 | 쿼리스트링을 URL에 반영 | `/work?category=ai` |

- 프로젝트명 단독 슬러그 **금지** — 검색되지 않는다.
- ❓ **고객사명을 슬러그에 넣을지는 NDA·공개 동의 확인 필요** → §14 Q7. 기본 결정: **고객사명 제외**, 동의 확인된 건만 사후 추가.
- 확정 후 변경 시 **301 리다이렉트 필수**.

### 4.3 Insight 카테고리 재구성안 🟡 — *클라이언트 요청 과제*

클라이언트가 **"우리 핏에 맞게 재구성해서 제안"**을 직접 요청한 항목이다.

| # | 카테고리 | 슬러그 | 이 카테고리가 존재하는 이유 | 대표 아티클 |
|---|---|---|---|---|
| 1 | **일하는 방식** | `how-we-work` | **핵심 소구점과 직결.** 포트폴리오 대신 프로세스를 보여주는 자리 | "우리가 3주 만에 랜딩을 만드는 순서" |
| 2 | **AI 활용 공유회** | `ai-playbook` | 내부에서 AI를 어떻게 쓰는지 공유 → "AI 최적화 인재" 증명 | "Orca를 실무에 붙인 1주차 기록" |
| 3 | **발주 가이드** | `client-guide` | **유입 확보용 마케팅 콘텐츠.** 발주자의 검색 의도를 정면으로 겨냥 | **"요즘 바이브 코딩으로 외주하는 업체가 많은데 조심해야 합니다"**, "바이브 코딩을 잘하고 못하는 기준은 무엇인가" |
| 4 | **빌더 노트** | `builder-note` | 빌더가 직접 작성 → **빌더 프로필로 연결** → 개인 자산화 | "이 프로젝트에서 내가 내린 판단 3가지" |

**설계 의도** — 1·2번이 "우리는 잘한다"를 증명하고, 3번이 검색 유입을 만들고, 4번이 빌더 자산화 구조를 돌린다. 3번은 클라이언트가 미팅에서 직접 제시한 소재를 그대로 카테고리로 승격시킨 것이다.

### 4.4 유튜브 탭 위치 — A/B안과 권고 🟡 — *클라이언트 요청 과제*

| | **A안: Insight 하위 탭** (똑개 현행) | **B안: 별도 상위 탭 `/content`** ← **권고** |
|---|---|---|
| GNB depth | 2 depth (Insight → 유튜브) | **1 depth** |
| UTM 전환 측정 | 유입이 Insight에 섞여 분리 어려움 | **"콘텐츠 탭에서 몇 명이 유튜브로 갔는가"가 그대로 측정됨** |
| 자산 비중 반영 | 유튜브가 부속물로 보임 | **이솝 님 유튜브가 핵심 자산임을 구조로 표현** |
| GNB 항목 수 | Work / Insight / 문의 (3) | Work / Insight / 콘텐츠 / 문의 (4) — 여전히 간결 |
| 리스크 | 유튜브 클릭 경로가 깊어져 전환 손실 | Insight와 콘텐츠 경계가 모호해질 수 있음 → **"자체 글=Insight, 영상=콘텐츠"로 명확히 분리** |

> **권고 근거** — 클라이언트가 명시한 측정 목표가 *"인사이트 탭에서 실제로 몇 명이 유튜브로 전환됐는지"*다. 상위 탭으로 분리해야 이 숫자가 오염 없이 잡힌다.

### 4.5 빌더 프로필 구조 (IA만 확보, 기능은 §14 Q6에서 판단)

```
Work 상세 → 참여 빌더 표기 → 클릭
                              ↓
                   빌더 프로필 /builders/[slug]
                   · 참여한 다른 프로젝트
                   · 작성한 Insight 아티클
                   · 일하는 방식 한 줄 요약
                              ↓
                   그 자체를 이력서로 사용
```

**이 구조가 기능이 아니라 리스크 해소 장치인 이유** — 똑빌더의 AI 추천은 프로젝트 이력 기반이다. 빌더 스쿨 수료생은 이력이 없어 **추천 후순위로 밀린다.** 프로필·이력을 쌓는 구조가 그 후순위를 푸는 유일한 방법이다.

> 🟡 **3주 범위 처리 방침: IA와 라우트 자리만 확보하고, 프로필 상세 기능은 2차 릴리스로 이관한다.** 1차에서는 Work 상세에 빌더 표기까지만 구현한다. → §14 Q6

## 5. 페이지별 화면 기획

### 5.1 홈 `/` — 섹션 구성과 인터랙션 배정

**이 표가 이 기획서에서 가장 중요한 표다.** 성공 조건 ①(딸깍 금지)을 만족시키는 실체가 여기 있다. **인터랙션이 섹션마다 전부 다르고, 의도적으로 아무것도 움직이지 않는 섹션이 2개 있다.**

| # | 섹션 | 목적 | **배정 인터랙션** |
|---|---|---|---|
| **S1** | **Hero** — "바이브 코딩으로 외주를 해드립니다" | 3초 안에 정체성 전달 + 1차 CTA | 텍스트 **스태거 등장** + 배경 그라디언트 **느린 이동** |
| **S2** | **문제 제기** — "바이브 코딩 외주, 이런 곳은 조심하세요" | 발주자의 실제 불안을 먼저 말함 | **콘텐츠 Fixed + 스크롤 연동** (문구가 스크롤에 따라 교체) |
| **S3** | **일하는 방식** — 기획→디자인→개발→검수 4단계 | ★ 핵심 소구점 | **가로 스크롤 연동** (스크롤 = 프로세스 진행) |
| **S4** | **검증 체계** — 똑빌더 기반 상향 평준화 | 품질 우려 해소 | ⛔ **애니메이션 없음 (의도적 정지)** — 신뢰 정보는 차분하게 |
| **S5** | **맞춤 매칭** — "개발사가 아니라, 당신 서비스에 맞는 개발자" | 차별화 선언 | **마우스 호버 인터랙션** (카드 hover 시 상세 전개) |
| **S6** | **Work 프리뷰** (3~4건) | 실적 제시 | 카드 **Fade-in (아래→위)** + 이미지 **패럴랙스** |
| **S7** | **Insight 프리뷰** (3건) | 전문성 제시 | ⛔ **애니메이션 없음 (의도적 정지)** — 읽는 영역 |
| **S8** | **콘텐츠·유튜브** | 이솝 님 유튜브 유입 | 썸네일 **화면 전환 퍼짐 효과** |
| **S9** | **FAQ** | 마지막 반론 해소 | 아코디언 **높이 전개** + **URL 슬러그 분기** (§7.2) |
| **S10** | **최종 CTA — 문의하기** | 전환 | 버튼 **마이크로 인터랙션**만 (과한 연출 금지) |
| **F** | **Footer** | 대체 연락 경로, 개인정보처리방침 | 없음 |

**설계 원칙 3가지**
1. **인접한 두 섹션은 절대 같은 인터랙션을 쓰지 않는다.**
2. **S4·S7은 의도적으로 정지한다.** — *"실제로 텍스트가 슬라이드 되지 않는 영역도 있고, 그런 것들이 사람이 했다고 느껴지거든요."* (17:54)
3. **CTA는 S1과 S10 두 곳으로 제한한다.** 근거는 §7.3의 실측 사례 — 버튼을 늘리면 전환이 죽는다.

### 5.2 Work `/work`, `/work/[slug]`

| 화면 | 구성 | 비고 |
|---|---|---|
| 목록 | 카테고리 필터(쿼리 URL 반영) + 카드 그리드 | 🟡 검색·정렬은 1차 범위 제외 (건수 50건 초과 시 재검토) |
| 상세 | 히어로 이미지 / 프로젝트 개요 / 문제→해결 서술 / **사용 기술** / **참여 빌더 표기** / 결과물 링크 / 관련 프로젝트 / 하단 문의 CTA | ❓ **오픈 시점 콘텐츠 미정** → §14 Q4 |

> ⚠️ **Work 탭의 최대 리스크** — 신규 브랜드에는 실적이 없다. 클라이언트는 *"워크가 있으면 지금 저희는 똑똑한 개발자에서 한 거니까 이거 자체가 저희 일"*이라며 **똑개 실적 전용 가능성**을 시사했다(30:57). 3사 협업 관계상 전용 가능 여부와 표기 방식 확인이 필요하다. **목업에서는 똑개 실적 전용을 전제로 그리되 🟡 배지를 붙인다.**

### 5.3 Insight `/insight`

- 좌측 **카테고리 네비** (§4.3의 4종) + 우측 아티클 리스트
- 상세: 제목 / 발행일 / **작성자(빌더면 프로필 링크)** / 본문(Tiptap 렌더) / 관련 글 / 하단 문의 CTA
- 🟡 자체 작성 본문에는 **외부 canonical을 걸지 않는다.** 걸면 우리 페이지가 색인에서 빠져 SEO 요구사항과 정면 충돌한다.

### 5.4 콘텐츠·유튜브 `/content`

- 영상 카드 그리드 (이솝 님 유튜브 / 빌더스쿨 수업 콘텐츠)
- **모든 외부 이동 링크에 UTM 부착** (§7.4) — 이 탭의 존재 이유
- 카드 클릭 시 **사이트 내 상세로 보낼지, 유튜브로 직행할지**: 🟡 **직행 + UTM**을 권고 (측정 목적이 명확하고 구현이 단순)

### 5.5 문의하기 `/contact` — pluug 연동

```
[/contact 페이지] → pluug 폼 → 제출 → [/submit 완료 페이지] → GA4 전환 기록
                                              ↓
                                    pluug 리드 적재 → 영업사원 배정 → 수주
```

| 항목 | 방침 |
|---|---|
| 폼 | 🔒 **pluug 사용.** 자체 폼을 만들지 않는다 (자체 폼이 되는 순간 개인정보 수집 주체가 우리가 되고 CRM 범위가 딸려 온다) |
| 연동 방식 | 🟡 **임베드 vs 직링크 2안을 목업으로 제시**하고 미팅에서 택일. 구현 참고는 **똑똑한 개발자 사이트** |
| 전환 측정 | 🟡 pluug의 **"제출 후 이동 링크"를 우리 도메인 `/submit`으로 지정** → 제출 완료가 GA4에 잡힘. `/submit`은 **noindex + sitemap 제외** |
| 대체 경로 | 🟡 Footer에 **이메일** 노출 (pluug 단일 장애점 대비) |
| 개인정보 | 🟡 `/privacy` 라우트와 동의 문구 **자리만 확보**. 문안은 클라이언트 제공·승인 후 채운다 |
| ❓ 미확정 | pluug 계정·폼 설정 권한 주체, API/임베드/리다이렉트 중 어느 방식인지 → §14 Q5 |

### 5.6 관리자 페이지 — **범위가 좁다. 넓히지 않는다.**

🔒 확정된 범위(D3):

| 탭 | 기능 | 비고 |
|---|---|---|
| **Insight(블로그) 관리** | 목록 / 작성·수정·삭제 / 발행 상태 / 썸네일 / **Tiptap 에디터** | 🔒 Tiptap 필수 (수업 가이드라인 + 미팅 명시) |
| **Work 관리** | 프로젝트 CRUD / 참여 빌더 연결 / 슬러그 입력 | 슬러그 입력 필드 **필수** (§4.2) |
| **빌더(유저) 관리** | 빌더 계정 목록 / 권한 / 활성·비활성 | 여기서 '유저'는 **개별 바이브 코더(빌더)**, 일반 고객이 아님 |
| **승인 대기** | 빌더가 올린 프로젝트 **검토 → 승인/반려** | 🔒 *"빌더가 로그인해 자신의 프로젝트를 업로드 → 최종 관리자가 승인"* |

🔒 **불포함:** 매칭 기능 / 리드·CRM(문의는 pluug가 관리, 우리 DB에는 **콘텐츠만** 저장) / 별도 운영 대시보드.

🟡 **권한 모델 (팀 제안)**

| 역할 | Insight | Work | 빌더 관리 | 승인 |
|---|---|---|---|---|
| **운영 관리자** | CRUD + 발행 | CRUD + 발행 | CRUD | ✅ |
| **빌더** | 본인 글 작성·수정 (발행은 승인 후) | 본인 프로젝트 등록·수정 | 본인 프로필만 | ❌ |

> ⚠️ **승인 게이트를 반드시 넣는다.** 빌더가 검토 없이 고객 노출 콘텐츠를 바로 공개하는 구조는 위험하다. 기수가 늘수록 계정이 계속 증가하므로 **발급·회수 절차**도 함께 정의한다.

## 6. 디자인 원칙 — 성공 조건 ①

### 6.1 "딸깍 느낌" 판별 기준

| ✅ 사람이 만든 것으로 느껴지는 조건 | ❌ AI 딸깍의 전형 |
|---|---|
| Fade-in(아래→위) / 마우스 호버 / 콘텐츠 Fixed+스크롤 연동 / 화면 전환 퍼짐 — **섹션마다 다르게** | **모든 섹션의 모든 텍스트가 동일한 "아래→위"** 애니메이션 |
| **애니메이션을 의도적으로 안 넣는 영역**을 둔다 | 전부 다 움직인다 |
| 컴포넌트가 목적에 따라 설계됨 | 같은 카드 컴포넌트를 전 섹션 반복 |

- ❌ **경계 사례: Ten AI** — 전 섹션 동일 애니메이션. 클라이언트가 직접 지목한 반례.
- ✅ **참고 사례: 똑똑한 개발자** — 섹션마다 다른 인터랙션 + 의도적 무애니메이션.
- ⚠️ **단순 모방 금지** — 예컨대 "헤더가 넓어지는 동작"이 정말 좋은 UX인지 스스로 검토하고 판단 근거를 남긴다. (클라이언트 요청 과제 A6)

### 6.4 접근성 기준선 🟡 (추가 비용 ≈ 0이므로 기본 적용)

`html lang="ko"` / 페이지당 h1 1개 / `main` 랜드마크 / 스킵 링크 / 이미지 alt 전수 / 버튼·링크 접근명 / 아코디언 `aria-expanded`+`aria-controls` / **`prefers-reduced-motion` 대응** / 포커스 표시 유지.

## 7. 데이터 트래킹 설계 — 성공 조건 ②

### 7.1 목적을 혼동하지 않는다

> **URL 슬러그를 분기하는 목적은 SEO가 아니라 GA 트래킹이다.** 목적을 혼동하면 구현이 달라진다.

### 7.2 URL 슬러그 분기

- 똑개 FAQ가 옵션에 따라 URL이 바뀌는 이유: **화면 전환만 하면 GA에 안 잡히기 때문.** (`/faq/aiax` ↔ `/faq/it`)
- 활용: AI/AX가 기본값인데 사용자가 계속 IT를 클릭한다면 → **메뉴 순서를 바꿔야 한다**는 의사결정 근거가 된다.
- 🟡 **우리 사이트 적용 대상:** FAQ 토픽 / Work·Insight 카테고리 필터(`?category=`) / 유튜브 탭 진입.

### 7.3 요소 단위 이벤트 — 버튼 하나가 전환을 죽인다

| 시점 | 상태 | 문의 유입 |
|---|---|---|
| 평시 | 정상 | 주 10~20건 |
| 변경 후 1주 | FAQ 옆에 **"소개서 다운받기"** 버튼 추가 | **0건** |
| 버튼 제거 후 | 원복 | **주 10~20건 회복** |

원인은 **사용자가 문의하기를 누르지 않고 소개서만 받고 이탈**한 것. → **CTA를 늘리지 않는다. 늘릴 때는 반드시 측정 가능한 형태로 만든다.**

🟡 **GA4 이벤트 규약 (팀 제안)**

| 이벤트명 | 발화 지점 | 파라미터 |
|---|---|---|
| `page_view` | 전 페이지 | 기본 |
| `cta_click` | 모든 문의 CTA | `location`(hero/footer/work_detail/insight_detail) |
| `work_detail_view` | Work 상세 | `slug`, `category` |
| `insight_detail_view` | Insight 상세 | `slug`, `category`, `author_type` |
| `youtube_outbound` | 콘텐츠 탭 → 유튜브 이동 | `video_id`, `utm_campaign` |
| `faq_topic_change` | FAQ 토픽 전환 | `topic` (URL 분기와 세트) |
| `contact_submit` | `/submit` 도달 | 전환 지표 |

> `/submit` 직접 방문으로 인한 가짜 전환을 막기 위해 `referrer` 조건 또는 토큰으로 필터링한다.

### 7.4 UTM 체계 🟡

목표: **"Insight/콘텐츠 탭에서 실제로 몇 명이 유튜브로 전환됐는가"** 를 유튜브 스튜디오에서 확인.

```
?utm_source=builder-group
&utm_medium=content          (또는 insight / work)
&utm_campaign=<아티클 슬러그 또는 영상 주제>
&utm_content=<노출 위치: hero_card / list_item / related>
```

### 7.5 계정·권한 🔒

- **GA4는 고객 계정을 받아서 작업한다.** *"고객 계정 받아서 작업 진행합니다"* (질문.xlsx, 8/8)
- 서치콘솔·네이버 서치어드바이저도 동일 원칙(고객사 명의 → 우리에게 권한 부여).
- GitHub·Vercel은 우리 계정에서 개발 후 **종료 시 고객사로 이전**. 🟡 **하자보수 기간 동안 접근 권한 유지**를 이관 시 함께 요청한다.

## 8. SEO 범위 — **스스로 늘리지 않는다**

🔒 *"기본적으로 SEO만 잘 되면 된다. GEO는 기본적으로 따라온다. 그것까지 보실 필요는 없고, 그냥 테크니컬적인 세팅만 해 주시면 됩니다."* (33:37)

| 포함 (테크니컬 세팅) | 제외 |
|---|---|
| 메타 타이틀·디스크립션 / OG·트위터 카드 | GEO·AEO 별도 대응 |
| `sitemap.xml` / `robots.txt` / `llms.txt` | 키워드 광고·유료 집행 |
| JSON-LD 구조화 데이터 (Organization, Article, BreadcrumbList) | 백링크 작업 |
| canonical / 301 리다이렉트 규칙 | 콘텐츠 대량 발행 |
| 목록·상세 **서버 렌더링** / 이미지 최적화 / Core Web Vitals | |
| 대상: **구글 + 네이버** | |

> ⚠️ 클라이언트가 덧붙인 경고: **테크니컬 세팅이 완벽해도 콘텐츠를 AI로 딸깍해서 계속 쓰면 결국 저품질로 떨어진다.** 콘텐츠 운영 주체가 유념할 사항이며 이번 구축 범위는 아니지만, **인계 문서에 명기한다.**

## 9. 기술 구성

🔒 수업 가이드라인 + 미팅에서 확정된 스택. **환경을 단일화하고 다른 인프라는 지원하지 않는다.**

| 레이어 | 선택 | 근거 |
|---|---|---|
| 프론트/서버 | **Next.js (App Router)** | 확정 스택. 서버 렌더링으로 SEO 요구 충족 |
| 데이터 | **Supabase** | 확정 스택. AWS·GCP 등 타 인프라는 **지원 대상 제외** |
| 배포 | **Vercel** | 확정 스택 |
| 에디터 | **Tiptap** | 🔒 필수. 관리자 콘텐츠 작성 전용 |
| 리드 수집 | **pluug** | 🔒 필수. 우리 DB에 리드를 저장하지 않는다 |
| 분석 | **GA4 (+ Search Console / 네이버 서치어드바이저)** | 고객 계정 |

🟡 **구현 원칙**
- 브라우저에서 Supabase를 직접 호출하지 않는다 (키·스키마 노출 방지). **서버 컴포넌트에서 페치.**
- Tiptap 저장 콘텐츠는 **서버에서 sanitize**한다. 본문 내 `h1` 사용 차단(제목이 h1).
- 공개 페이지는 **ISR + 어드민 저장 시 온디맨드 갱신**. "즉시 반영"이 아니라 **"60초 이내 반영"**으로 안내한다.
- 저장 테이블: `works` / `insights` / `builders` / `categories` — **리드 테이블은 만들지 않는다.**

## 12. 협업 및 의사결정 체계 🔒

### 12.1 시안 선정 — **투표 금지**

```
각자 개인별 제작 → 리드 2인이 검수 → 베스트 1~2개 픽 → 탈락 사유 작성 → 전체 제출
```

| 규칙 | 원문 취지 |
|---|---|
| **투표 금지** | *"가장 워스트는 투표를 하는 거. 투표를 하는 건 최악입니다."* |
| **의사결정은 한 명이 총대를 멘다** | **"최종 결정은 저희 둘이서 하겠습니다"를 명시적으로 선언**할 것 |
| **탈락자를 납득시킬 필요 없다** | *"납득시킬 필요가 없어요. 그렇기 때문에 팀장과 팀원이 존재하는 거거든요."* |
| **탈락안도 함께 제출** | 탈락 사유를 문서로 남겨 클라이언트에게 함께 전달 |
| **클라이언트에게 여러 안을 동시에 주지 않는다** | 조율 과정에서 일정·예산을 벗어나는 '제7의 안'이 생기는 것을 방지 |

### 12.2 커뮤니케이션

| 항목 | 규칙 |
|---|---|
| 채널 | **단체방 1개로 통합** (슬랙). 방을 쪼개지 않는다 |
| 질문 | **모아서 한 번에** 남긴다 — 클라이언트가 실시간 확인이 어렵다 |
| 무응답 시 | **전화로 재촉한다.** *"진짜 그렇게 해 주셔야 돼요"* |
| 기록 | 미팅 내용은 방에 기록해 둔다 |
| 내부 | 매일 아침 **데일리 회고**, 주 1회 클라이언트 보고 |
| 응답 기준 | 🟡 업무시간 기준 **당일 1차 응답**. 답을 못 주더라도 "확인해서 O시까지 회신드리겠습니다"를 먼저 남긴다 |

### 12.3 팀 운영 전제

- 🔒 **월 400만 원을 벌 때까지는 무조건 팀으로 일한다. N빵이 기본 전제.**
- 🔒 리드에게 요청된 관찰 항목: **협업이 어려운 사람이 있는지 체크.** 단, 어려워도 N빵은 유지하고 **어떻게 이끌지**가 중요.
- 🔒 **클라이언트와의 소통 능력도 평가 대상.**
- ❓ 정산 배분안(1,000만 원 / 2,000만 원 기준)은 클라이언트가 문서화해 공유 예정 → §14 Q9.
